# 中断からの再開

引数なしの `/vouch`（Codex は `$vouch`）は、セッション終了・コンテキスト圧縮・クラッシュ・意図的な停止の後に、成果物と監査ログから現在地を確かめて作業を続けるための入口である。根拠は決定記録 §5・§11。

## 前提と対象

[doctor](doctor.md) を先に実行し、Node と配布の診断が成功したことを確認する。失敗・起動不能・不正な結果なら、その診断と「再開は未実施」を返す。Node 不在時に成果物だけで縮退しない。[R-PROJECT-7]

対象は利用者が指定した Intent、次にセッション開始の要約にある Intent とする。どちらもなければ vouch/intents の候補を示し、候補が一つならそれを使い、複数なら選択を求める。更新日時、直前のログ、approved の宣言だけで選ばない。存在しなければ未作成と伝え、作成しない。

## 現在地の確かめ方

セッション開始フックが渡す「Vouch 再開要約」は、成果物の frontmatter と監査ログをフックが読んだ観測である。要約を出発点にし、[status の説明](status.md)と同じ根拠（成果物の宣言値、確認点、判断依頼の対応、監査の読めた範囲）で必要な箇所を読み直す。要約に「一部のみ読めた」とあれば、未回答なしと断定しない。

状態ファイル、状態キャッシュ、再開用のメモを作らない。現在地は毎回成果物と監査ログから導く。成果物と監査が食い違う時、frontmatter が重複・未知の値の時、ログに不正な行や重複 ID がある時は、修復・再採番せずにそのまま示す。[R-PROJECT-3]

## 再開の進め方

現在地、確認点、未回答・既定適用済みの判断依頼、証拠の不足を根拠付きで短く示し、次の作業を一つ提案する。作業は該当するステージ Skill（Intent・Design・Build・Verify）の手順で進め、再開の Skill の中で別の手順を作らない。

- Intent が draft なら、未確認の確認点は人の `vouch confirm`、承認は `vouch review` と `vouch approve` で人が入力する。要約・ファイルの存在・既定適用・構造化質問の回答を確認や承認に数えない。[R-PROJECT-1]
- approved の宣言に承認の証跡がなければ Build に進まず、その事実を示す。
- 未回答の判断依頼は[判断依頼の記録](questions.md)に従う。止まるのは既定案が作れない時だけである。[R-PROJECT-6]
- 承認・確認・回答・既定適用の記録をモデルが監査へ書き足さない。記録はフックと登録したコマンドだけが行う。[R-PROJECT-3]

利用者が状態の表示だけを求めた時は [status](status.md) として扱い、作業を始めない。
