# Git 操作の検査と DoD の実行・記録

## 範囲と根拠

[Issue #6](https://github.com/otomatty/vouch-workflows/issues/6) の契約と検証記録です。決定記録 §4 の禁止リスト（テストを通すためのテストの改変・削除、`main` への直接 push、禁止リストに載っていないことの禁止）と不変条件（契約とテストより先に実装をコミットしない）、§11 のフックの責務（契約 → テスト → 実装の順序、DoD の実行と記録、禁止リストの機械的部分）、図7（Intent のブランチ上の contract → test（red）→ feat（green）のコミット順）、§18 Q6（コミットメッセージの型は英語固定）に従います。§18 の決定と Q1〜Q6 は変えません。

[書き込み保護](write-guard.md)と[承認の境界](approval-boundary.md)を前提にします。今回追加するのは次の2つです。

- 既存の PreToolUse ガード `vouch-guard-writes.mjs` の最後の段として、登録したシェルツール（両ハーネスの Bash）の `git push` と `git commit` の検査。登録は変えません。
- 手動コマンド `vouch-dod.mjs`。`vouch/rules.md` の DoD を実行し、コマンド・出力・結果・所要時間を build-log.md と監査（`hook.check`、`check: dod`）に記録し、結果をモデルへ返します。

フックは判断しません。コミットの件名と変更パス、監査レコードの項目、コマンドの終了コードを機械的に照合し、禁止事項と不変条件に当たる時だけ理由付きで遮ります。何を契約とするか、テストの変更が妥当か、DoD の失敗の原因と修正はモデル・reviewer・人が決めます。

## 機械的に検査する範囲と判断が要る範囲

| 事項 | フックが機械的に行うこと | モデル・reviewer・人が判断すること |
| --- | --- | --- |
| `main` への直接 push | push 先の枝名が保護対象なら拒否する | 例外を認めるかは人。人はハーネスの外で push できる |
| 合格を装うテストの改変・削除 | `test(<Unit>)` 型以外のコミットで、テストファイルを変更・削除する（追加は除く）ものを拒否する | `test` 型のコミットでのテストの変更が妥当かは reviewer と人が差分と Brief で見る |
| 契約 → テスト → 実装の順序 | コードを変えるコミットの型と Unit の形式、実装のコミットの前の契約（DoD 合格）とテスト（DoD 不合格）のコミットを検査する | 何を契約として固めるか、テストが受入基準を検証しているか、DoD の不合格が意図した理由かはモデルと reviewer |
| DoD の実行と記録 | rules.md のコマンドを実行し、出力と結果を build-log.md と監査に残す | 失敗の原因分析と修正はモデル。合格条件の文面の解釈とコマンドの選定は人 |
| 本番データの操作 | 検査しない。接続先・資格情報・コマンドの意味が環境ごとに異なり、機械的に対象を特定できない | rules.md の「禁止事項と適用範囲」に対象・根拠・例外の判断者を書き、reviewer と人が判断する |
| 禁止リストにない Git 操作（Intent のブランチへの force push、rebase、reset、stash など） | 遮らない。禁止リストにない操作を禁止しない | 必要かどうかはモデル。PR で人が見る |

## コミットの型と Unit

コミットの件名（1行目）の書式は `<type>(<Unit>): <説明>` です（`<type>(<Unit>)!: <説明>` も可）。型の一覧と順序の要件は `core/registry/build.json` が正典です。

| 型 | 意味 | 同じ Unit で先に必要なコミット |
| --- | --- | --- |
| `contract` | 型・スキーマ・データ定義 | なし |
| `test` | テスト。テストファイルを変更・削除できる唯一の型 | なし |
| `feat` | 新しい振る舞いの実装 | DoD が合格した `contract`、その後に DoD が不合格の `test` |
| `fix` | 不具合の修正 | DoD が不合格の `test` |
| `refactor`、`docs`、`chore` | 振る舞いを変えない変更 | なし |

`<Unit>` は、設定した Intent の intent.md の計画の表（[承認の境界](approval-boundary.md)の書式）にある Unit ID です。`feat` の要件は TEST-10（新機能は型と入出力の契約を先にコミットし、型検査が通ってからテストを書く）、`fix` の要件は「バグ修正は再現テストが先に落ちるコミットを含む」に対応します。

## 検査する規則

コミットの変更パスのうち、先頭の要素が `vouch`（正規化後）でないものをコードとします。コードを変えないコミット（Intent の下書き、decisions.md、承認コミット、build-log.md など）は検査しません。マージコミットも対象外です。コードを変えるコミットには、次を上から順に検査し、最初に当たったものを理由にします。

| 規則 | 理由 ID | 条件 |
| --- | --- | --- |
| 型 | `VOUCH-COMMIT-TYPE` | 件名が `<type>(<Unit>): <説明>` の書式でない、または型が一覧にない |
| Unit | `VOUCH-COMMIT-UNIT` | Unit が計画にない。intent.md がない、計画が読めない場合も同じ |
| テスト | `VOUCH-COMMIT-TEST` | 型が `test` でなく、テストファイルの変更・型の変更・削除（`--no-renames` の M・T・D）を含む |
| 順序 | `VOUCH-COMMIT-ORDER` | 型に要件があり、同じブランチのそれより前のコミットで要件を順に満たせない |

テストファイルは、`build.json` の `tests.directories` のどれかを親ディレクトリに持つパス（`test/`、`tests/`、`__tests__/`、`spec/`、`specs/`）と、ファイル名が `tests.names` のどれかに一致するパス（`test_*`、`*.test.*`、`*_spec.*` など）です。要素は小文字にし、末尾のドットと空白を除いて比べます。一覧にない命名のテストは保護しません。golden や fixture も `tests/` の下なら保護対象です。

順序の要件は、要件の型を左から順に、前の要件を満たしたコミットより後で探します。`feat(U1)` なら、DoD 合格の証跡がある `contract(U1)` を探し、その後で DoD 不合格の証跡がある `test(U1)` を探します。別の Unit、別のブランチのコミット、証跡のないコミットは要件を満たしません。

## 証跡

証跡は、設定した Intent の監査の `hook.check`（`check: dod`）レコードのうち、次をすべて満たすものだけです。

- synthetic でない。`intent` が設定した Intent。`commit` と `clean: true` を持つ
- ID が `newId(<commit>, JSON.stringify(["hook.check", "dod", <intent>, <output.sha256>]))` と一致する

合格の証跡は `result: pass` のレコード、不合格の証跡は `commands` に終了コードが0以外のコマンドを持つレコードです。未設定の行だけによる不合格や、起動できなかったコマンド（終了コードなし）は不合格の証跡に数えません。記録はコミットの SHA に結び付くため、DoD は対象のコミットを作ってから、`vouch/` の外に未コミットの変更がない状態で実行します。

## 対象のコミット列

コミット列は、HEAD から到達でき、保護対象の枝（`refs/heads/<名前>` と `refs/remotes/*/<名前>`）のどれからも到達できない、マージを除くコミットです（古い順）。`main` から分岐した Intent のブランチ自身のコミットにあたります。Git の作業ツリーの最上位がプロジェクト root（別名を含めて `locate` で照合）でない場合と、Intent を設定していない場合は、順序の検査をしません。

## `git commit` の検査

シェルのコマンドを POSIX の字句で単純コマンドに分け、`git` の大域オプション（`-C`、`-c`、`--git-dir`、`--work-tree` など）を読み飛ばしてサブコマンドを得ます。`cd <固定の語>` と `-C` は、入力の cwd から Git の `-C` を重ねて同じ位置で Git を起動します。変数・`~`・`-` などの動的な移動の後は位置が分からないものとして扱います。

コミット時の検査は、件名が機械的に読める時だけの早期の検査です。

- 件名は最初の `-m`・`--message`（`-am` などの束ねたフラグ、`--message=` を含む）の値の1行目です。値が `$(cat <<'EOF'` の here-document なら本文の1行目です。それ以外で `$` やバッククォートを含む値、`-F`・`-C`・エディタ・`--fixup` などでは件名を読めないので、コミット時には検査しません。
- 変更は `git diff --cached` です。`-a`・`--all`、または同じコマンドの前に `git add`・`rm`・`mv` がある時は、HEAD との差分（`git diff HEAD`）と追跡していない新しいファイル（`git ls-files --others --exclude-standard`、追加として扱う）に広げます。過剰側に倒すため、同じ行で一部だけを stage しても、作業ツリーの他の変更を含めて判定します。
- 規則は上の表と同じです。予定のコミットを、ブランチのコミット列の後ろに置いて検査します。

`--amend` は特別に扱いません（置き換えられる HEAD もコミット列に含めて判定します）。コミット時に読めなかった件名や、ハーネス外で作られたコミットは、次の push の検査が実際のコミット列で判定します。push の検査が正本です。

## `git push` の検査

push 先の枝名を次の規則で求め、保護対象（`build.json` の `protected`、既定は `main`）なら `VOUCH-GIT-PUSH` で拒否します。Intent の設定の有無に関わらず検査します。

| 書き方 | push 先 |
| --- | --- |
| `<src>:<dst>`、`+<src>:<dst>`、`:<dst>`（削除） | `<dst>`。`refs/heads/` を除く |
| `<名前>`、`--delete <名前>` | `<名前>` |
| `HEAD` | 現在の枝（`git symbolic-ref --short HEAD`） |
| refspec なし | 現在の枝と `@{push}` の枝の両方 |
| `--all`、`--mirror`、`--branches`、`*` を含む refspec | すべての枝（保護対象を含むとみなす） |
| `--tags` だけ | 枝を push しない |

`-n`・`--dry-run` は push しないので検査しません。push 先に `$` などの実行時に決まる語がある、または現在の枝が必要なのに位置が分からない時は、確かめられないので拒否します。

push 先が保護対象でなく Intent を設定している時は、プロジェクトのリポジトリのコミット列全体に上の規則を当て、最初に当たったコミット（短縮 SHA と件名）を理由にして拒否します。コミット列・intent.md・監査を読めない時は `VOUCH-GIT-UNVERIFIED` で拒否します（fail-closed）。

## Git の起動

フックは `spawnSync("git", ["--no-optional-locks", ...])` をシェルなしで、`runtime.json` の gitTimeoutMs（1.5秒）で起動します。使うのは読み取りのサブコマンド（`rev-parse`、`symbolic-ref`、`for-each-ref`、`log`、`diff`、`ls-files`、`status`）だけで、ネットワークに出ません。`node:child_process` は Git のコマンドがある時に初めて読み込みます。

## DoD の実行と記録

### 起動と前提

モデルはシェルで `node .claude/hooks/vouch-dod.mjs`（Codex は `.codex`）を実行します。`runtime.json` の commands に登録した手動コマンドなので、書き込み保護は doctor と同じく配布ディレクトリの名指しを許します。プロジェクト root はコマンドのファイルの位置から決め、Intent は `VOUCH_INTENT` から読みます。stdin は読みません。

| 前提 | 満たさない時 |
| --- | --- |
| `VOUCH_INTENT` がある | `DOD-SCOPE`。何も実行・記録しない |
| intent.md が approved で、その版に承認の証跡がある（Build 開始の境界と同じ照合） | `DOD-PLAN`。同上 |
| `vouch/rules.md` の `<!-- sec:dod -->` 節に表があり、行が1つ以上ある | `DOD-RULES`。同上 |

### DoD の表の書式

`sec:dod` 節の最初の Markdown 表の3行目以降を1行ずつ読みます。1列目が対象、2列目がコマンドと作業ディレクトリです。2列目の最初のインラインコード（`` `npm test` ``）がコマンド、2つ目（`` `packages/api` ``）が root からの作業ディレクトリ（省略時は `.`）です。インラインコードのない行（「未設定」など）は未設定で、実行しません。表の中の `|` は `\|` と書きます。合格条件と証拠の保存先の列は人のための記述で、フックは終了コード0だけを合格とします。

### 実行

行の順に、プラットフォームのシェル（`shell: true`）でコマンドを実行します。stdin は空、環境変数は引き継ぎ、Vouch の打ち切り時間はありません（HOOK-13 は DoD の実行を時間予算の対象外とする）。ハーネスのツールの打ち切りが上限になります。作業ディレクトリは FileStore の包含の検査を通し、root の外やリンクなら実行せず不合格にします。出力は標準出力の後に標準エラーを続けたものです。

実行の前に HEAD の SHA と `git status --porcelain -z -uall --no-renames` を読み、`vouch/` の外に変更がなければ clean とします。clean でない、またはコミットがない実行の記録は、証跡としてコミットに結び付きません。

### 記録

build-log.md（`vouch/intents/<intent>/build-log.md`）の末尾に、次の形の1件を FileStore のロック付きの置き換えで追記します。出力は末尾の200行（`build.json` の `dod.outputLines`）を残し、省いた行数を書きます。

````markdown
<!-- dod -->
## DoD 2026-09-29T00:00:00.000Z

- Intent: `260929-orders`
- Commit: `<40桁の SHA>`
- Result: fail

### Unit tests

- Command: `npm test`
- Directory: `.`
- Result: fail (exit 1, 1234 ms)

```text
<出力>
```
````

その後に監査へ `hook.check` を1件追記します。項目は `check: dod`、`result`（すべての行が設定済みで終了コード0なら pass）、`duration_ms`、`missing`（未設定の行の数）、`commit`（あれば）、`clean`、`commands`（行ごとの対象・コマンド・作業ディレクトリ・結果・所要時間・終了コード）、`output`（build-log.md に追記した1件の SHA-256）です。ID は証跡の節の導出です。build-log.md の追記の後で監査の追記に失敗した時は、その実行は証跡になりません。

### 結果の返し方

stdout に doctor と同じスキーマ（`doctor-report.schema.json`、ID は `DOD-*`）の JSON を1行で出します。`DOD-COMMIT`（コミットと clean）、行ごとの `DOD-COMMAND`（結果と build-log.md の行番号）、`DOD-RECORD`（監査の ID）です。すべて ok なら終了0、それ以外は終了2です。失敗の判断と修正はモデルが行います。予期しない I/O エラーは `DOCTOR-IO` の終了2です。

## 理由 ID

| 理由 ID | 条件 |
| --- | --- |
| `VOUCH-GIT-PUSH` | 保護対象の枝への push、または push 先を確かめられない |
| `VOUCH-COMMIT-TYPE` | コードを変えるコミットの件名が型と Unit の書式でない |
| `VOUCH-COMMIT-UNIT` | Unit が計画にない |
| `VOUCH-COMMIT-TEST` | `test` 型以外のコミットでテストファイルを変更・削除する |
| `VOUCH-COMMIT-ORDER` | 実装の型に必要な、証跡付きの契約・テストのコミットが先にない |
| `VOUCH-GIT-UNVERIFIED` | コミット列・変更・intent.md・監査を読めない |

stderr は `<理由 ID>: Bash <対象>; <説明>` の1行で、対象は push のコマンド、コミットの件名、または push で当たったコミットの短縮 SHA と件名です。制御文字は `?` に置き換えます。書き込み保護と Build 開始の境界の理由が優先です。

## 行数予算の変更

この機能のロジックは lib の `git.mjs`（Git の起動・件名・変更・コミット列・証跡・規則）、`git-guard.mjs`（push と commit の検査）、`dod.mjs`（DoD の実行と記録）に置き、単体テストとミューテーション検査の対象にします。着手前の lib 合計は 2,892 行で、予算 3,000 行に収まりませんでした。フック1本 150 行の予算にも収まらず、フックの分割は登録の変更と重複を伴います。

P-7 は予算の超過に Opus 5.5 での失敗の実証を求めますが、今回は実証をしていません。Issue #6 の実装のために、リポジトリの所有者の判断で `budgets.json` の libTotal を 3,000 行から 3,500 行に引き上げました。他の予算は変えていません。

## 検出・拒否できる範囲と限界

| 経路 | 扱い |
| --- | --- |
| 登録したシェルツールの `git push` で保護対象の枝を名指す・既定で選ぶ | 拒否 |
| 登録したシェルツールの `-m` のコミットで規則に当たる | 拒否 |
| 件名を読めないコミット、ハーネス外のコミット、`--amend`・rebase で作ったコミット | コミット時は検査外。push 時にコミット列で拒否 |
| 別名（`git config alias.*`）、`sh -c`・`eval`・スクリプト・変数を介した Git、登録していないツール | 検査外 |
| `git push` 以外の経路での共有（`git send-pack`、別のクローンからの push、Web の操作） | 検査外 |
| 保護対象の名前が `main` 以外のリポジトリ | `build.json` にない名前は保護しない |
| 一覧にない命名のテストファイル | 保護しない |
| `test` 型のコミットでのテストの改変・削除、DoD の不合格が意図した理由か | 許可する。reviewer と人が判断する |
| DoD の実行の途中でのファイルの変更、並行する別の実行 | 防がない。記録は clean の判定の時点の状態を表す |
| 本番データの操作 | 検査しない（判断が要る範囲） |
| DoD のコマンドの内容の妥当性 | 検査しない。rules.md に書かれたものを実行する |

## 検証の方法

契約・型、失敗する先行テスト、実装の順にコミットします。既存の fixture、golden、元仕様、移行元資料を合格のために変更しません。

- unit：`git.mjs` の件名・変更・コミット列・証跡・規則を、注入した Git と監査レコードで検査します。`git-guard.mjs` の push 先の解釈・コミット時の件名の抽出・理由の優先を、偽の Git の応答で検査します。`dod.mjs` の前提・表の読み取り・実行・build-log.md と監査の記録を、メモリの FileStore と偽のプロセスで検査します。
- hooks：Claude 2.1.283 / Codex 0.153.4 の版付き Bash の PreToolUse から派生した synthetic 入力を、実際の Git リポジトリのサンドボックスで runHook により実行します。許可・拒否、同じ入力の再送、不正入力、別ブランチ・別 Unit の証跡、偽の監査レコード（synthetic、ID の導出の不一致、clean でない実行）を検査します。DoD コマンドは、承認済みの Intent を持つサンドボックスに配布をコピーして子プロセスで実行します。
- registry：`build.json` の閉じたスキーマと、`hook.check` の拡張、DoD の報告の ID を Ajv と実行時の検証器で検査します。
- 性能：検査系の p95 2秒未満を、push の検査の20回の子プロセスと合成負荷で測ります。DoD の実行は HOOK-13 の対象外です。

## 検証記録

実装後に記載します。
