# 監査ログ検証の重複処理

## 変更する契約

`AuditStore` の API と監査イベントのスキーマは維持します。`find()` が返すレコードは呼び出し側で変更できる独立した値とし、変更が次の読み込みや追記に影響しないことを契約に明記します。

検索と有効な非空バッチの追記は必ずファイルを読み直します。直前に検証した全文と完全一致する場合だけ、解析・スキーマ検証済みのレコードを再利用できます。時刻、サイズ、ID の一致だけでは再利用しません。追記は既存のロックを取った後に読んだ全文と照合します。内容が変わっていれば全行を再検証し、破損・ID衝突を拒否します。ファイル境界、ロック、sync、原子的置換は変更しません。空バッチは従来どおり I/O を行いません。

スキーマ評価では `type` の定数が一致しない候補を早く除外します。一致する候補と `legacy.*` の条件、未知フィールド、必須項目の検証は維持し、Ajv との比較で確認します。イベント種別の一覧をコードに複製しません。

ID 衝突時の内容比較に使う正規化は、衝突したレコードだけに行います。書き込み予定の行は検証済みレコードと別の Map に置きます。途中でバッチを拒否しても、未保存行を次の検索で返しません。

## 検証方針

既存の20回の子プロセス性能テストを失敗の再現として維持します。今回の開始時点でも p95 は361.8msで、200ms未満の基準は未達でした。起動時間を差し引いた値を合格判定に使いません。

回帰テストでは、取得したレコードのネストした値の変更、同じ長さの外部更新、検索後の破損・削除を検査します。既存の全文保存、UTF-8、リンク、原子的更新の検査も継続します。

処理内の改善は、synthetic と明示した2,000行のログに対する検索と追記を20回計測して比較します。これはプロセス起動と実ディスクを含まない補助測定です。HOOK-13 の合否とは分けて記録します。

## 補助測定

契約のコミットは `32344f8`、回帰テストと測定スクリプトは `64fb7c3`、拒否したバッチの回帰テストは `204f0be` です。追加した回帰テストは変更前から通る安全性の検査です。速度不足の再現は既存の子プロセス性能テストです。

```sh
node scripts/benchmark-audit.mjs
```

`tests/fixtures/audit/session.started.jsonl` を使い、synthetic の指定がない入力は拒否します。各試行は独立したメモリストアを使います。ID を変えた既存2,000行と追加1行が、全文一致で残ったことも確認します。

Windows / Node.js 24.13.0、同じ入力・20回での比較です。

| 検査対象 | 変更前 p50 / p95 | 変更後 p50 / p95 |
| --- | --- | --- |
| 既存0行の検索・追記 | 0.083 / 0.210ms | 0.035 / 0.085ms |
| 既存2,000行の検索・追記 | 75.6 / 100.7ms | 18.1 / 22.8ms |

2,000行の補助測定の p95 は約77%短縮しました。ファイルの読み込み、sync、プロセス起動・終了はこの表に含みません。記録系フックの200ms予算を満たしたという結果ではありません。

2026-09-27、HEAD `90c7fcd`、Windows / Node.js 24.13.0 で、6条件を交互に20回ずつ測りました。Codex 0.153.4 の版付き fixture の cwd と session_id を変更した synthetic 入力を使い、各記録条件を独立した Intent に保存しています。stdout・stderr と終了コードを毎回確認しました。起動・終了を含む外側の時計で測り、最初の試行も除外していません。
