# 監査ログ検証の重複処理

## 変更する契約

`AuditStore` の API と監査イベントのスキーマは維持します。`find()` が返すレコードは呼び出し側で変更できる独立した値とし、変更が次の読み込みや追記に影響しないことを契約に明記します。

各操作は必ずファイルを読み直します。直前に検証した全文と完全一致する場合だけ、解析・スキーマ検証済みのレコードを再利用できます。時刻、サイズ、ID の一致だけでは再利用しません。追記は既存のロックを取った後に読んだ全文と照合します。内容が変わっていれば全行を再検証し、破損・ID衝突を拒否します。ファイル境界、ロック、sync、原子的置換は変更しません。

スキーマ評価では `type` の定数が一致しない候補を早く除外します。一致する候補と `legacy.*` の条件、未知フィールド、必須項目の検証は維持し、Ajv との比較で確認します。イベント種別の一覧をコードに複製しません。

## 検証方針

既存の20回の子プロセス性能テストを失敗の再現として維持します。今回の開始時点でも p95 は361.8msで、200ms未満の基準は未達でした。起動時間を差し引いた値を合格判定に使いません。

回帰テストでは、取得したレコードのネストした値の変更、同じ長さの外部更新、検索後の破損・削除を検査します。既存の全文保存、UTF-8、リンク、原子的更新の検査も継続します。

処理内の改善は、synthetic と明示した2,000行のログに対する検索と追記を20回計測して比較します。これはプロセス起動と実ディスクを含まない補助測定です。HOOK-13 の合否とは分けて記録します。
