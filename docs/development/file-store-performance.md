# 記録用ファイル操作の性能改善

## 契約

Windowsの記録性能3件はp95 200ms未満を満たしていません。20回・CPU数並列・各ケース5秒・check全体90秒を維持し、起動時間の差し引き、再試行による合格扱い、既存fixtureやgoldenの変更はしません。

FileStoreの公開APIはPromiseのまま、既定のネイティブファイル操作を同期APIへ変更します。フック専用の子プロセス内で完結するI/Oが、ファイル操作ごとにワーカープールへ往復するのを避けます。同期操作はその子プロセスのイベントループを止めます。共有サーバー向けの汎用FileStoreとして推奨する変更ではありません。

既定のドライバーはnode:fsだけを使い、realpathSync.nativeでrootを正規化します。ファイルシステムの読取結果・パスの属性はキャッシュしません。rootと包含の確認、祖先と対象のリンク・型の検査、更新前と置換前の再検査は維持します。

書込手順はロック取得、既存内容の再読取、更新関数、排他的な一時ファイル作成、UTF-8書込、fsync、close、再検査、rename、所有した一時ファイルとロックの後片付けです。fsyncや検査の省略、別プロセスのロックの削除、失敗した更新の成功扱いはしません。従来の最終検査後の外部競合に対する限界も変わりません。

注入する操作は同期値またはPromiseを返せます。FileOperations / FileWriteHandleのJSDoc契約を先に固定します。FileStoreはどちらもawaitし、同期throw・Promiseの拒否を公開APIでは同じ拒否として扱います。実行時のnpm依存は追加しません。

## 先行する診断

変更前fa144f8の単独交互計測では、Node 24.13.0のp95は空プロセス147.8ms、ESM空プロセス175.2ms、固定時計のみ153.8ms、記録なし223.1ms、通常記録286.7ms、固定時計付き記録310.2msでした。起動と環境変動も大きく、この変更だけで予算達成を保証しません。

FileStoreの20回の読取・更新を既存Promise実装と試験用同期ポートで比較すると375.1ms / 235.9msで、lstatは両方640回でした。プロセス全体の交互診断でも、同じ試験preloadで各20回を観測し、既存方式p50 371.7ms / p95 459.0ms、同期ポートp50 349.7ms / p95 435.8msでした。プロセス全体の数値は別条件の診断値で、契約検査の合否とは区別します。

1回の起動を計測した観測用preloadでは、全体192.3ms、Node内の経過104.8ms、lstat 32回に9.7ms、mkdir 2回に4.8msでした。JSの処理時間だけを性能予算とみなすことや、観測値から起動時間を差し引いて合格させることはしません。

## テストと残件

既定ドライバーがFSREQPROMISEを発行しないことを、async_hooksの読取専用観測と実ファイルの内容で確認します。非同期の注入ポートの互換性、write / sync / close失敗時の原本維持とロック解放、置換前のリンク再検査も検証します。変更前後のfs.mjsを対象にミューテーションを測定し、生存変異の差を記録します。lib全体の基準測定や夜間CIの代わりにはしません。

監査書き込みの真正性保証、モデルや人による手編集の遮断、他の製品フックは今回の対象外です。

## 実装と先行テスト

契約をce62723、先行テストを1e53f61でコミットしました。実装前の6件中、キューへの要求数を検査する1件が28件を観測して失敗し、失敗時の保全を検査する5件は成功しました。実装後は同じ操作の要求数が0件になりました。ファイル内容と公開APIがPromiseであることも同じテストで確認します。

既定ドライバーのfsyncSyncとcloseSyncは、実際の関数を呼ぶ観測用ラッパーで順序とファイル記述子の一致を確認します。返り値やエラーを模造する検査ではありません。追加のミューテーションで検査の不足が見つかったため、BOMを含むUTF-8の保持、COM/LPT名の拒否と似た正常名の受理、Errorではないポート例外をENOENTとして無視しないことも追加しました。

## 日本語パスでの片付け

最初の同期実装の全体検査では、配布先で4つの記録プロセスが3221226505で異常終了しました。観測用ラッパーと新しい所有ディレクトリで、renameの後のrmSyncに切り分けました。このPCのNode 24.13.0では、日本語を含むパスの不存在ファイルに対するrmSync(path, {force:true})だけでも同じ終了コードを再現し、unlinkSyncはENOENTを返しました。Node本体やOS内の原因までは特定していません。

専用子プロセスの回帰テストで、日本語・空白・引用符を含むroot配下の作成、再更新、UTF-8内容、ロック解放を検査します。片付け対象は所有した一時ファイルなので、同期ドライバーはunlinkSyncを使い、実際のErrorのENOENTだけを許容します。権限エラーなど他の失敗は拒否し、ディレクトリの再帰削除はしません。
