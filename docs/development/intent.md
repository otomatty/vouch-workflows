# Intent 下書きの契約

## 範囲と根拠

決定記録 §5・§6・§7・§10・§12・§14・§15 と、優先する §18 を根拠に、vouch-intent Skill と日英の intent.md / decisions.md テンプレートを追加します。Intent の目的・AC・非ゴール・理想形と最小実装・調査根拠・分割・Unit とリスク・検証方法・確認点を下書きとして用意する範囲です。

この段階で承認イベントの記録・真正性検査、確認点の記録、引用・知識鮮度の機械検査、explorer は実装しません。状態機械や自動遷移も追加しません。実行時 JavaScript と JSDoc API の追加はなく、既存 doctor と Markdown / JSON のデータを使います。今回の成功を Intent 全体の実装完了とは報告しません。

## 入力・出力と承認の境界

入力は新しい要望、または利用者が明示した既存 Intent の修正依頼です。Skill の対象は配布された同一プロジェクトで、doctor の成功を前提とします。Node 不在・診断失敗なら編集せず診断を返します。指定のない対象や衝突を更新日時から決めず、必要なら対象だけを確認します。

新規の出力先は vouch/intents/<YYMMDD-slug>/intent.md と decisions.md です。日付は実際の作業日とし、slug は依頼の内容から作ります。解決後のプロジェクト内のパスと既存ファイルを確認し、リンクや ../ を辿る出力先には書きません。既存 Intent は指定された下書きだけを差分編集し、既存の人の言葉・引用・ID・判断履歴を保持します。status が draft 以外、欠落、不明の場合は上書き・降格せず、修正案を返します。既存の承認を新しい版へ流用しません。

新規 Intent の frontmatter は status: draft だけです。intent-draft-frontmatter.schema.json は新規下書き専用の検査であり、過去の approved 等を不正にする全状態のスキーマではありません。テンプレートの未記入欄と Mermaid 図は記入用で、完成した成果物や証拠ではありません。decisions.md は人が読む記録であり、監査の代用ではありません。

承認フックが未実装の間は、実際の人の発言を出所付きで decisions.md に残せても、approved への変更・承認コミット・Build 開始はしません。今回の終了は根拠付きのレビュー可能な下書き、論点ごとの確認状況、未実装の承認経路を報告することです。追加の承認を繰り返し求めることで未実装の経路を代用しません。

## 計画と判断の内容

受入基準は AC-n で成功・失敗・境界条件を表し、各 AC を Unit と検証方法・証拠の予定へ対応付けます。既存コードと知識を読み、現状の根拠と推測を分け、理想形との差分、根本原因、見落としたユースケース、後回しにするリファクタを示します。explorer がない時は現在のモデルが読み取り調査し、未実施の再走査や鮮度保証を主張しません。

1 Intent = 1 PR = 1 Brief = 1つの振る舞いの変更を分割の基準とします。Unit は5以下を目安とし、機械的な上限にはしません。準備リファクタは振る舞い不変の別案、公開 API・スキーマ・データ定義の契約変更は H の最小の Intent として提案します。Unit の依存順、AC、リスク根拠、Design 要否を示します。品質層・破壊検査・全階層の依存監査は quality-layers.json を参照し、未実行の検査を合格扱いしません。

確認点は workflow.json と rules.md に従い、AC、非ゴールと最小実装、分割・Unit・リスク、必要時の設計採択を区別します。H は Unit ごとの確認も追加します。過去の回答を参照して同じ判断を再質問せず、前提が変わった場合だけ変更点を示します。未回答でも既定案で下書きの独立部分を進めますが、人の採択・承認へ置き換えません。

判断依頼の Q-n は状況、2〜4選択肢、各案のメリット・デメリット・根拠、推奨、未回答時の既定、ブロックと影響範囲を持ちます。「何もしない」も検討し、載せない時は理由を記載します。既定案を作れない時は理由を示します。人の回答は原文と出所を保ち、モデルの D-n、仮定、未回答・既定適用を区別します。Brief §6 / §7 へ後で引き継ぐ対象を残します。架空の質問・回答・監査イベントは作りません。

Intent のユーザー操作フロー図は常設し、brownfield の影響範囲図も条件付きの記入枠として含めます。条件と図の種類は diagrams.json が正典です。対象・挙動・影響・参照元を実際の調査で埋め、未記入の図を要件を満たした証拠にはしません。日英で同じ節 ID・図 ID・質問欄・判断欄を同じ順に保ちます。識別子は英語固定、本文の言語は利用者の指定、既存 rules.md、workflow の既定の順に選びます。

## 正典と検証

intent-authoring.json は下書き専用の frontmatter、節 ID、質問・選択肢・判断の欄、Unit の目安、選択肢数を持ちます。ファイル名・ステージ・確認点・品質・図を既存レジストリと重複定義しません。対応する JSON Schema を先にコミットし、型検査、失敗するテスト、実装の順で進めます。

content で下書きの frontmatter、日英の節・欄の一致、必須・条件付き図の種類、Skill の公開情報と参照、原本と配布の全文一致を検査します。新規4テンプレートの golden は UPDATE_GOLDEN=1 を明示して追加し、既存 golden は変えません。packaging は両配布の追加ファイル集合と参照先を検査します。registry では schema と不正な下書きメタデータの拒否を検査します。

手製のモデル評価入力は tests/eval/intent に置き、synthetic:true / execution:not-run とします。構造検査の成功をモデルの作成・承認動作の合格や実機イベント採取とは扱いません。enforcement-map の実装済み欄は構造と配布の検査に限定し、承認・質問・引用・確認点・生成物の意味評価は pending に残します。元仕様、移行元資料、既存 fixture、実行時依存、時間予算は変更しません。
