## 設計原則

### D1. ガードはガードレールであり、セキュリティ境界ではない

[書き込み保護](write-guard.md)の「検出・拒否できる範囲と限界」のとおり、生成したスクリプト・変数・eval・設定・別名を介した間接的な書き込みは検査外とする。導入範囲を増やしても、この線は動かさない。シェルの語は、字句どおりに読める範囲と、既存の「保護対象と同じ形の綴り」の判定だけで扱う。変数・チルダ・拡張 glob を展開して保護対象を推定する処理は持たない。`python -c` や生成スクリプトで同じ書き込みができる以上、シェルの展開だけを追っても境界にならないためである。意図的な回避への対策は、ハーネス自身の権限とサンドボックスに任せる。

### D2. リポジトリの内容は、実行するコードを選ばない

clone しただけで入ってくるリポジトリの内容（`vouch/config.json` など）が選べるのは、データだけとする。

- ランチャーは、自分自身の本体のコードだけを実行する。設定が別の本体を指す場合は実行せずに終える。最初の実装はこの不変条件を守っており、本書で契約として明記する。
- Intent は `vouch/config.json` だけから決める。環境変数 `VOUCH_INTENT` でランチャーの選択を上書きしない。
- Vouch をそのリポジトリで有効にするかどうかは、リポジトリが決める。リポジトリは `vouch/config.json` を置かないだけで、いつでも Vouch を無効にできる。このため「リポジトリが偽って処理を譲らせる」ことを検証で防いでも意味がない。防ぐ対象はエージェントによる書き換えであり、`vouch/config.json` と `.vouch/` は既にガードの保護対象である。

### D3. 個人共通の導入は、ユーザー単位のフックを登録しない

最初の実装では、個人共通の導入がユーザー単位（`~/.claude/settings.json` など）にもフックを登録していた。しかしこのフックは、有効化済みのプロジェクトでは常にプロジェクト側の登録に処理を譲り、未有効化のプロジェクトでは何もしない。実際の記録とガードは、常に `init` がプロジェクトへ書く登録から起動していた。

働きのない登録は、ユーザー単位の登録ファイルの保護、処理を譲る条件の検証、外部の作業ディレクトリからのシェル解析といった指摘を生んだ。そこで登録をやめる。個人共通の導入は本体・Skill・エージェントだけを置き、フックは `init` が書くプロジェクトの登録だけから起動する。Codex のユーザー単位の `config.toml` も編集しない。

### D4. インストーラは決まったファイルしか編集しない

インストーラが作成・編集・復元するパスは、ハーネスごとの固定の一覧に限る。

| 種別 | 許可するパス |
| --- | --- |
| `hooks` | そのハーネスの登録ファイル（`.claude/settings.json`、`.codex/hooks.json`、`.cursor/hooks.json`） |
| `block` | `AGENTS.md`、`CLAUDE.md`、`.codex/config.toml` |
| `file` | Vouch の Skill・エージェント（名前が `vouch` で始まる）、`.cursor/rules/vouch.mdc`、`.codex/config.toml` |

導入記録の `owned` は、読み込む時にこの一覧と種別の組で検証する。`file` の `previous` は常に `null` とする（既存のファイルを `file` として所有しないため）。導入記録の内容を digest や再生成で照合する仕組みは持たない。

配布（`--dist`）と個人共通の導入先は、利用者自身のものとして信頼する。改ざんや不完全な自作配布は、doctor の digest 照合で偶発的な破損として検出するところまでとする。

### D5. パスは実体で比べる

本体とプロジェクトのパスは realpath で比べ、綴りでは比べない。記号リンク・junction・大文字小文字の違いで別物と判定しないためである。削除系の操作は、対象がプロジェクトのルートまたはその祖先なら拒否する。シェルにある既存の規則を、ファイル操作ツールにも同じく適用する。

### D6. 生成するコマンドはシェルに依存させない

- 生成するコマンドは素の `node` で始め、パスは二重引用符で囲む。環境変数の展開（`${X}`、`$env:X`、`%X%`）は使わない。同じ文字列が sh・Git Bash・PowerShell・cmd で動く。
- 導入先のパスに `"`・`$`・`` ` ``・`%`・`<`・`>`・改行を含む場合と、Windows 以外でバックスラッシュを含む場合は、導入を拒否する。生成する Markdown のリンクにも同じ制約が効く。
- プロジェクト単位のフックと手動コマンドは、カレントディレクトリから上へランチャーを探す短い起動式（`node -e`）を共有する。起動式は環境変数を読まない。
- Claude のプロジェクト登録は、ハーネスが展開する `${CLAUDE_PROJECT_DIR}` の `args` 形式を維持する。シェルを通らないためである。
- 起動したランチャーは、Claude ではハーネスが展開したプロジェクトのルートを使い、それ以外ではカレントディレクトリ（Cursor はハーネスが示すルート）から上へ `vouch/config.json` を探してプロジェクトを決める。

### D7. ハーネスのネイティブ契約に合わせる（Cursor）

- preToolUse は `{"permission":"allow"}` または `{"permission":"deny","user_message":…}` を返す。beforeSubmitPrompt は `{"continue":true}` または `{"continue":false,"user_message":…}` を返す。未有効化・入力不正・内部エラーを含む全経路で、スキーマに合う応答を返す。
- `Delete` ツールは、ファイルの削除として保護対象を判定する。
- Shell の `working_directory` を相対パスの基点にする。
- 本文のない afterAgentResponse は、回答として記録しない。

### D8. 利用者の設定ファイルを解析して書き換えない（Codex の config.toml）

- プロジェクトの `.codex/config.toml` がなければ、Vouch の所有ファイルとして作る。`sandbox_mode` は書かない。
- あれば、必要な表（`[features]`・`[agents]`）がどの形でも定義されていない時だけ、マーカー付きのブロックを末尾に追記する。既にある表の中の値は編集しない。必要な値がなければ、追記する行を示して中止する。
- TOML の構文は検証しない。壊れた TOML は Codex 自身が報告する。複数行の文字列の中に表の見出しと同じ行がある場合など、行単位の判定が誤る形は既知の限界とする。

### D9. レビュー指摘の受け入れ基準（運用）

この PR の範囲の P1 だけを直す。P2 以下は Issue にして返信し、スレッドを解決する。本書の原則の外にある指摘は、原則を引いて「既知の限界」と返信する。自動レビューは push のたびに再実行しない。

### 後続 Issue の候補

P2 として報告された機能の不具合のうち、本書の設計変更で解消しないものを挙げる。どれも局所的な修正で済む。

- Claude の導入で `statusLine` を登録しない（Devin・Codex）。D2・D6 に沿って、`init` がプロジェクトの登録へ追加する。
- 中断で残ったインストーラのロックを回復できず、案内もない（CodeRabbit）。
- `--project` を省略した `remove --scope user` が、カレントディレクトリのプロジェクトを変更する（CodeRabbit）。
- `remove --scope user --project` の書き込み順で、失敗時に不整合が残る（CodeRabbit）。
- 選択しない側の導入記録・接続の読み込み失敗で、選択した側の `init`・`update` まで止まる（Codex 3件）。
- `init` が欠けた有効化・不正な Intent・欠けた本体を修復せずに成功を返す（Codex 4件）。
- ホームとプロジェクトが同じ、または入れ子の場合の扱い（Codex 2件）。
- 配布の読み取り中のディレクトリとファイルの入れ替え（Codex）。
- Windows で権限がない時の記号リンクのテスト（CodeRabbit）。

## 実装の結果

- P1 の修正は、D2〜D8 の原則ごとに失敗するテストを先にコミットしてから実装した。本体のコード（`core/`・`harness/`・`scripts/`）の変更は TypeScript への移行後の時点から15ファイル・+291／−205行である。

- D3 で個人共通の導入はユーザー単位の登録ファイルと `config.toml` を変更しなくなった。ランチャーの `user` スコープもない。
- 16〜20（シェルの展開）は実装していない。プロジェクト外で保護するのは、D5 の実体の比較で判定する実行中の本体だけである。
