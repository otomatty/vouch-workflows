# 導入範囲と対応ツール

2026-10-03、所有者が共通本体の個人共通・プロジェクト単位の導入と、Claude Code・Codex CLI・Cursor の3ツールを対象にする方針を決定した。本書は、決定記録 §15 のプロジェクト内配置と2ハーネスを前提とした範囲に優先する。元仕様は当時の記録として保持する。ステージ、承認、監査、品質、実行時依存の既存契約は引き続き参照する。

## 確定した対象と導入範囲

設計対象は Claude Code・Codex CLI・Cursor の3ツールとする。ほかのツールは今回の対象に含めない。

共通のワークフロー本体は、個人共通・プロジェクト単位の両方に導入できる。規則、知識、計画、成果物、監査ログは、どちらの導入方式でも作業対象のプロジェクトに保存する。

| 区分 | 配置先 | 責務 |
| --- | --- | --- |
| 共通本体 | 個人共通、またはプロジェクト内 | Skills、エージェントの共通定義、テンプレート、レジストリ、共通の検査・記録処理 |
| ツール別の接続部分 | 導入範囲に合わせて配置・登録 | Skills の読み込み、フックの入力・結果の変換、エージェントの起動、対象プロジェクトと本体の解決 |
| プロジェクト固有のデータ | 作業対象のプロジェクト内 | 設定、`vouch/rules.md`、`vouch/knowledge/`、`vouch/intents/`、移行元を保管する `vouch/archive/` |

個人共通の導入では、一つの本体を複数のリポジトリから利用できる。プロジェクト単位の導入では、チームが本体の版を固定して共有できる。個人共通に本体を置いても、異なるプロジェクトの規則や監査ログを共用しない。

## 実装で満たす契約

- Windowsの区切り文字だけをスラッシュへ正規化する。POSIXの本体パスに含むリテラルのバックスラッシュは保持し、Markdownリンクでは符号化する。個人共通のSkill・案内文書・手動コマンドと検証に同じ変換を使う。
- Codex TOMLの配列が改行なしのEOFで未終了の場合も、設定を追加する前に拒否する。配布の登録スナップショットは、有効なJSONオブジェクトであり、非空の登録テンプレートの必要な設定を含むことを導入・更新前に確認する。空・不正JSON・内容の不一致では両scopeのファイルを保持する。
- 本体の選択はファイルシステム上の同一性で比較する。プロジェクトルートをリンク・junction・大小文字の別表記から開いても、同じ本体のフックと手動診断を実行し、別の本体の重複実行は防ぐ。
- Codex の正の整数の agent depth は、符号・桁区切り・16進／8進／2進を含む正しい TOML 表記を元のバイトのまま保持する。0と負の値だけを必要な正の値へ変える。
- 本体のルートと作業対象のプロジェクトのルートを分離する。本体の配置場所から作業対象を決めない。プロジェクト固有の読み書きは、検証済みのプロジェクトのルートを境界とする。
- プロジェクトが指定した本体・版を優先する。Skills、エージェント、レジストリ、フックは同じ版の組として選び、各ツールの同名 Skill の探索順だけに版選択を任せない。
- 本体の導入とプロジェクトでの有効化を分離する。個人共通の導入は全リポジトリから利用可能にするためのもので、各プロジェクトへの適用は設定または明示呼び出しで決める。
- 既存のツール設定と `AGENTS.md` を保持できる導入・更新・削除方式を定める。Vouch が管理する項目を識別し、既存ファイル全体の上書きを導入手順にしない。
- 個人共通とプロジェクトの登録が共存する場合も、同じ操作のフックを二重に実行・記録しない。doctor は選択した本体・版・導入範囲と登録の重複を診断する。
- 共通の判断・検査・監査処理を `core/` に置き、ツールごとのイベント名、入力形式、遮断の返し方、登録形式は接続部分で扱う。対応数を増やしても、ワークフローの判断処理をツールごとに複製しない。

具体的な配置と操作は下記の導入コマンドの契約に従う。従来の `dist/claude/`・`dist/codex/` の直接配置も保持し、新しい導入方式はランチャーを通す。

## ツールごとの確認範囲

| 対象 | 現在の実装 | 未確認の範囲 |
| --- | --- | --- |
| Claude Code | 両スコープの導入・版選択・Skills・エージェント・フックを実装、自動テスト済み | 新しい導入方式の実ハーネスでの登録・信頼・発火 |
| Codex CLI | 両スコープの導入・版選択・Skills・エージェント・フックを実装、自動テスト済み | 新しい導入方式の実 CLI とサンドボックスでの本体参照・発火 |
| Cursor | 配布・両スコープの導入・JSON 接続を実装、手製入力による自動テスト済み | IDE Agent の Skills・エージェント・フックの読み込みと遮断、版付きの実機 fixture |

Cursor の公式 [プラグイン仕様](https://github.com/cursor/plugins/blob/main/schemas/plugin.schema.json)には Skills・エージェント・フックの定義があり、[公式プラグイン](https://github.com/cursor/plugins)を接続方式の参照元とする。これらの存在だけで、Vouch の承認記録や書き込み遮断が動くとは扱わない。

同じ製品でも、CLI・IDE・クラウド実行でフックや利用可能なツールが異なる。Cursor CLI や Codex の Desktop・IDE 拡張への対応は、対象製品名から推定せず、利用形態・バージョン・OS を明記した実機検証で判定する。

## 正式対応の判定

3ツールそれぞれについて、個人共通・プロジェクト単位の2方式を独立して確認する。正式対応の判定では、Skills の発見に加え、次を検証する。

- セッション開始と再開、フックの登録・入力・出力・遮断結果が実際のツールに伝わること。
- 人の明示入力からの確認・承認記録と、承認済み計画のない実装へのガードが、対象ツールの検査可能な経路で働くこと。
- 規則・知識・成果物・監査ログが対象プロジェクトに保存され、別のプロジェクトへ混入しないこと。
- builder / reviewer / explorer を意図した役割で起動し、Verify が Build と別のコンテキストで検証すること。
- 個人共通とプロジェクトの版選択、登録の重複、サブディレクトリと worktree からの実行、既存設定との共存を確認すること。

検証には版付きの実機入力を採取し、手製入力、配布の構造検査、実登録、実モデルの振る舞いを区別する。検査できない経路や取得できない計測値は、ツールごとに明記する。

## 実装との境界

配布生成は `dist/claude/`・`dist/codex/`・`dist/cursor/` を対象にする。本体とプロジェクトの分離、両スコープの導入・更新・削除・有効化・版選択、所有項目だけを変更する設定の接続を実装した。6通りの導入と監査の保存、更新時の版固定、プロジェクト優先、重複回避、移動後の起動、設定の保持、衝突・リンク拒否、失敗時の復元を自動テストする。Cursor の確認・承認・書き込み拒否・脇質問の回答は手製 JSON 入力で検査する。

既存の配布・実機検証の記録は当時の範囲を示す。本書の決定をもって、3ツール・2方式の検証が完了したとは報告しない。

## 導入コマンドの契約

導入は Node と Git だけで実行する `node scripts/vouch.mjs` を入口とする。`install` / `update` / `remove` は `--harness claude|codex|cursor` と `--scope user|project` を要求する。個人共通の対象は `--home`、プロジェクト単位の対象は `--project` で明示できる。省略時はそれぞれ利用者のホーム、現在のプロジェクトを使う。個人共通の導入後は `init --harness <対象> --project <作業先> [--home <導入先>] [--intent <Intent>]` でプロジェクトを有効化する。`doctor` は有効な本体・範囲・登録を読み取りで検査する。

Codexのプロジェクト登録は `VOUCH_PROJECT_ROOT` の事前設定を要求しない。実行時の作業ディレクトリから最も近い `vouch/config.json` を持つ祖先を探し、本体と対象プロジェクトを選ぶ。両導入範囲でルート・子ディレクトリ・移動後から起動でき、環境変数やstdinの偽のプロジェクト名をこの探索の代わりにしない。

Codex TOMLの複数行文字列は自動編集の対象外とし、導入・有効化の診断で `INSTALL-CONFIG` として変更前に拒否する。文字列内の `[features]` / `hooks = true` / `[agents]` を有効化済みの設定と誤認せず、doctorも成功と報告しない。通常の引用文字列とコメントは保持する。
通常の引用文字列が閉じないまま改行・ファイル末尾に達する場合も拒否する。二重引用文字列のバックスラッシュで改行を隠す場合も同じ扱いとし、不正な文字列内の見出しを有効化として報告しない。
エスケープを含む二重引用のキー名・テーブル名は自動編集の対象外とし、変更前に拒否する。Unicodeエスケープで管理対象名と同じ名前になるキーを別名として追加しない。設定値の引用文字列内のエスケープと、単一引用のリテラル名は保持する。
複数行配列も変更前に拒否する。配列内の `[true, false]` などをテーブル見出しと誤認して重複キーを追加しない。同じ行で閉じる入れ子配列、文字列やコメント内の角括弧は保持する。
`features.hooks` と `agents.max_depth` が子テーブルやドット形式の子キーとして宣言されている場合は、スカラー設定の追加と衝突するため変更前に拒否する。引用した名前と、さらに深い子テーブルも検査する。管理対象外の子テーブルは保持する。
親キー`features` / `agents`の代入との衝突は最初のテーブル見出しより前のルートだけで検査する。他のテーブルに属する同名キー・ドットキーを管理対象の親と誤認せず、導入・更新・診断・解除でその値を保持する。
対象のfeatures・agentsを配列テーブルとして定義する `[[features]]` / `[[agents]]` も、通常のテーブルを同じキーに追加する前に拒否する。引用したテーブル名にも同じ検査を行う。
Vouchが作成したテーブルヘッダーも所有記録に残し、解除後に設定が残らない場合はヘッダーを削除する。既存のヘッダーと、利用者の設定が残るテーブルは保持する。既存記録にヘッダーの所有情報がない場合は削除を推測しない。

本体は導入先の `.vouch/versions/<配布の digest>/<harness>/` に置く。配布の digest はファイル名とバイトから求め、既存の版を上書きしない。導入記録は `.vouch/installations/<harness>.json`、プロジェクトの有効化は `vouch/config.json` に記録する。プロジェクト内の本体は root 相対、個人共通の本体は絶対パスで指定する。`init` は既存のプロジェクト本体を個人共通の本体より優先する。有効なプロジェクト単位の導入記録がある場合は、個人共通の導入記録を読み込まない。無関係な個人共通の記録の不正JSON・ハーネス不一致・拒否するリンクを、独立したプロジェクトの再有効化を妨げる理由にしない。選択したプロジェクト本体と所有項目の検査は保持する。プロジェクト内に残った未選択の個人共通の接続記録 `.vouch/bindings/<harness>.json` も読み込まず、古い所有項目の復元計画を作らない。不正または古い記録はそのまま保持し、選択したローカルの有効化だけを更新する。
個人共通の導入後の初期化では、本体の絶対参照と導入先から求めた正規の版パスをファイルシステムの同一性で比較する。大文字・小文字などの異なる綴りが同じ場所を指す場合は受け入れ、同じバイトを別の場所へコピーした本体は拒否する。大文字・小文字を区別する環境では、別の導入先を同じ場所と推測しない。新しい個人共通の導入記録は導入時の本体の絶対参照を保持し、本体内の文書の照合とプロジェクトへの接続にも同じ綴りを使う。既存の相対参照の記録も受理するが、文書の改変を許可するために照合を緩めない。

導入の各書き込みは祖先と対象を新しく検査し、その操作で確認した親ディレクトリが存在する場合はmkdirを繰り返さない。一時ファイルのrenameが成功した後は元の一時パスを削除せず、そのパスを再利用した別の書き手のファイルも保持する。rename失敗時は自分が作成した一時ファイルを削除する。操作をまたぐメタデータのキャッシュは使わない。

配布の木を読む時はルートと祖先を最初に検査し、各項目の最新の実パスがそのルートと列挙した相対名に一致すること、最新の種別とリンク数を確認してから読む。祖先ごとのlstatを各ファイルで重ねず、途中でファイルやルートの祖先をリンクへ置換された場合も読み取り前に拒否する。各木の読み取りで検査をやり直し、UTF-8とバイト一致の検査も保持する。
列挙時のディレクトリと読み取り直前の通常ファイルなど、種別が変わった項目も拒否する。列挙時の種別で項目を読み飛ばし、不完全な木のdigestを受け入れない。

`init` がプロジェクト内の本体として選ぶのは `scope: project` の導入記録だけとし、個人共通の候補は `scope: user` に限る。個人共通の導入先と有効化するプロジェクトがファイルシステム上で同じ場所の場合、登録と所有記録が重なるため `INSTALL-SCOPE` で拒否する。別の `--project` を指定するよう案内し、既存の導入記録・設定・成果物は変更しない。既にプロジェクト単位で導入した本体の再初期化は保持する。

プロジェクト単位の本体がある場合、`init` は選択した版の `vouch/config.json` の有効化も行う。設定ファイルの欠落や対象ツールの項目が失われた場合も `v`・導入範囲・digest・本体参照・登録範囲を再設定し、他のツールや利用者の項目は保持する。既存の管理文書・Skills・フック登録と所有記録は再作成せず、設定の未対応の版や不正な `harnesses` は変更前に拒否する。

`install` と `update` は配布の `registry/installation.json` の `harness` が `--harness` と一致することを変更の計画前に検査する。不一致や欠落は `INSTALL-SOURCE` で拒否し、既存の導入記録・ネイティブ設定・プロジェクトのファイルを変更しない。別のツールの本体を登録してフックが未有効化として扱われる状態を作らない。

既存の導入記録を変更・削除する `install` / `update` / `remove` は、保存した `harness` と `scope` が要求したツール・導入範囲と一致することを計画前に検査する。不一致は `INSTALL-STATE` で拒否し、同じ配置先の別スコープの導入を変更しない。`init` の導入候補もツールの一致を必須とし、プロジェクト接続の所有記録は対象ツールの `scope: user` に限る。不一致では既存ファイルを保持し、正しい範囲での再実行を可能にする。

書き込みの事前検査は計画した全ファイルに行う。既存の内容と一致するファイルは置換せず、変更があるファイルだけを書き込む。同じ版の再導入・更新でも事前検査の競合検出を省略しない。

一つの変更計画では、ファイルの最初の検証済み読み取りを変更前のバイトとして保持する。同じファイルの参照や計画の追加で読み直して変更前の値を更新しない。計画中に他の処理がファイルを変更した場合も、書き込み直前の事前検査で最初の値との差を競合として拒否する。リンクやパスの検査は最初の読み取りと実際の事前検査・書き込みで行い、過去の検査だけで書き込みを許可しない。

配布の `registry/installation.json` が指定する登録・設定の写しは本体ルート内のパスに限定し、配布元の参照ファイルが存在することを必須とする。参照元が欠けている場合に空文字で置換せず、変更前に導入を拒否する。
登録名は `[a-z][a-z-]*.json`、任意の設定名は `[a-z][a-z-]*.toml` の単一ファイル名とし、配布doctorと同じ契約で変更前に検査する。ネストした既存ファイル、異なる拡張子、その他の名前を参照して導入成功を報告しない。

ネイティブの Skills・エージェント・フックはツールの探索先に登録する。設定の他の項目と無関係なフックを維持し、所有するフックだけを置換・削除する。`AGENTS.md` / `CLAUDE.md` への追加は Vouch のマーカー付きブロックとし、削除時はそのブロックだけを除く。Cursor の `.cursor/rules/vouch.mdc` は所有する専用ファイルとして生成し、既存の同名ファイルとは衝突として扱う。管理対象のファイルが導入後に変更されていた場合は更新・削除を拒否し、変更を上書きしない。事前検査で衝突を確認してから変更し、変更中の失敗では元に戻す。

個人共通とプロジェクトのフックが共存する場合、プロジェクト登録を優先する。個人共通のフックは、有効化していないプロジェクトでは記録・ガードを行わない。ランチャーは本体と対象プロジェクトを分離し、既存の製品フックに検証済みの root と Intent を渡す。手動の doctor / DoD / lifecycle / question / migrate / report も同じ対象を使う。

Cursor の接続ではネイティブの JSON 入出力と共通フックの入力・結果を変換する。ネイティブのイベント名・ツール名を共通処理に混入させず、監査の harness は `cursor` として区別する。確認・承認の入力識別子は Cursor が渡す `generation_id` を使い、欠損時には生成して補わない。採取できていない入力は synthetic として検査し、実機で確認したとは報告しない。

個人共通の本体は、プロジェクト内のシンボリックリンクや junction を経由した登録ツールの書き込みも拒否する。対象の表記に `.vouch` があるかだけで判断せず、FileStore が解決したプロジェクト外の絶対パスと、実行中の本体の信頼済みの実パスを比較する。本体内のファイル作成・編集・パッチ・シェル書き込みと、親ディレクトリからの削除を対象とし、無関係な外部ファイルや読み取り専用コマンドは拒否しない。

解決できた外部ファイルが選択済み本体と無関係なら、パスに `.vouch` を含むだけでは管理対象としない。ファイルツール・パッチ・シェルの固定パスに同じ境界を適用する。プロジェクト内の導入設定と、選択済み本体への別名や親ディレクトリの削除の保護は保持する。

Cursor の `Delete` は共通のファイル削除として登録する。監査・ロック・管理する導入・承認済みの成果物とそれらを含むディレクトリの削除を拒否し、アプリケーションのファイル削除にも既存の Build 承認境界を適用する。Shell の `working_directory` がある場合は、その場所を共通入力の cwd とし、相対指定はネイティブの cwd（欠損時はプロジェクトルート）から解決する。別のツールの同名フィールドで cwd を変更せず、対象プロジェクトや Intent の選択も変更しない。

登録したファイル削除がプロジェクト外の親ディレクトリを指定する場合も、解決済みの対象がプロジェクトを含むという `contains` の情報を祖先の保護へ使う。親ディレクトリごとの削除で監査・本体・承認済み成果物を消す迂回を許可しない。無関係な外部ディレクトリの削除と、親ディレクトリを参照する削除以外の操作はこの祖先保護で拒否しない。

## 配置と版の運用

| 対象 | 個人共通の接続先 | プロジェクトの接続先 |
| --- | --- | --- |
| Claude Code | `<home>/.claude/skills/`・`agents/`・`settings.json` | `.claude/skills/`・`agents/`・`settings.json`、`CLAUDE.md` |
| Codex CLI | `<home>/.agents/skills/`、`<home>/.codex/agents/`・`hooks.json`・`config.toml` | `.agents/skills/`、`.codex/agents/`・`hooks.json`・`config.toml` |
| Cursor | `<home>/.cursor/skills/`・`agents/`・`hooks.json` | `.cursor/skills/`・`agents/`・`hooks.json`、`.cursor/rules/vouch.mdc` |

個人共通の本体を使うプロジェクトにも、その版の Skills・エージェントとプロジェクト用フックを接続する。プロジェクトで選ぶ版の組を固定し、ツールの探索順やグローバル側の更新で組が混ざらないようにする。本体のコード・レジストリ・テンプレートは個人共通に残し、規則・知識・監査をそこへ書かない。

個人共通のプロジェクト接続の所有記録は `.vouch/bindings/<harness>.json` に置く。個人共通の更新はこの接続を変更せず、`init` で最新の個人共通版へ切り替える。プロジェクト内の本体がある場合はそちらを選ぶ。プロジェクト内の版と接続は相対参照で移動可能にし、個人共通の選択は導入先の絶対パスを持つため、その利用者の環境に依存する。

`remove --scope project` はプロジェクト本体の登録、または個人共通本体へのプロジェクト接続を解除する。`remove --scope user` は個人共通の登録を解除し、`--project` を明示した場合だけそのプロジェクトの接続も解除する。現在の作業ディレクトリだけではプロジェクトを解除しない。両方を変更する場合は両方の導入ロックを保持し、一方の競合ではどちらも変更しない。どちらも版のディレクトリ、規則、知識、成果物、監査を保持する。未使用版の清掃は実装していない。

解除対象の接続は、パスの大小文字などの表記差だけで異なる本体と判定せず、ファイルシステム上の同一性で確認する。異なる導入先の本体へ接続するプロジェクトは解除しない。

個人共通の登録とプロジェクト接続を同時に解除する場合は、全ファイルを事前検査した後、プロジェクト側の変更を先に書き込む。プロジェクト側で失敗した時に個人共通の導入記録を失い、再試行できなくなる順序を避ける。書き込み失敗時は、復元の一部が失敗しても残る変更の復元を続ける。復元できなかったパスと元の失敗を `INSTALL-ROLLBACK` で報告する。OS が復元の書き込みも拒否する場合、完全な復元は保証できず、報告したファイルの修復が必要になる。

導入ロックには所有プロセスの PID と取得時刻を保存する。既存ロックは自動削除せず、競合時にロックのパスと、実行中の導入処理がないことを確認してから手動解除する手順を伝える。権限不足などのエラーをロック競合に置き換えない。

Claude の管理する登録には読み取り専用の `statusLine` を含める。既存の利用者の `statusLine` は保持し、Vouch が追加したものだけを更新・削除する。個人共通の表示もプロジェクトが選んだ版と Intent を読み、未有効化のプロジェクトでは何も表示・記録しない。
WindowsのstatusLineコマンドはGit BashとPowerShellの両方で起動できる構文にする。相対パスを使えない本体の参照は、引用符・ドル・バッククォートなどを含む絶対パスもシェルに解釈させずNodeへ渡す。接続したプロジェクトの明示指定も保持する。

自動statusLineは、選択した本体の正規パス・導入記録・プロジェクト接続・所有項目・保存配布と実本体の一致を実行前に検査する。表示を実行するコードは登録元の本体に固定し、プロジェクトのconfigから別のJavaScriptへ切り替えない。プロジェクトが整合した配布・digest・導入記録を用意していても、それを登録元と同じ信頼の証明とは扱わない。表示対象のIntentと成果物はプロジェクト設定から読み、検査も表示も書き込まない。

導入パスから生成する Markdown のリンク先は構文文字を符号化し、インラインコードはパス内のバッククォートに応じた区切りを使う。改行を含む制御文字のある導入パスは変更前に拒否する。

`doctor` は選択した配置・digest、所有する登録と文書、配布の原本と本体の一致を検査する。Skill の doctor も、本体を別の FileStore で読み、実際のプロジェクト登録の不足・重複を検査する。どちらもハーネスの信頼設定やモデルの遵守を証明しない。Codex の既存モデル・プロバイダー・sandbox と正の `agents.max_depth` は保持し、必要な `features.hooks` だけを有効化する。既存設定がない場合も `sandbox_mode` を生成せず、導入後に利用者が別の設定を追加しても、更新・解除で導入の所有外の sandbox 方針を残さない。対象テーブルのインライン・ドット形式など安全に追加できない TOML は、変更前に拒否する。

管理する本体の Skill doctor は、保存した配布の全ファイルから digest を再計算し、導入記録と一致することを確認する。本体のフック・registry・templates・AGENTS.md は、保存した配布に導入時と同じ参照変換を適用した内容と比較する。空でない改変、配布の改変・欠落・追加、リンクを正常と報告しない。この検査はプロジェクトと個人共通の両scopeで読み取り専用とする。

ネイティブの本体参照と明示プロジェクト引数は Claude の `CLAUDE_PROJECT_DIR`、Cursor の `CURSOR_PROJECT_DIR` を使う。Codex のプロジェクト登録は作業ディレクトリから最寄りの `vouch/config.json` を持つ祖先を探し、そのルートを引数に渡す。`VOUCH_PROJECT_ROOT` の事前設定は不要とする。手動コマンドはプロジェクトルートと子ディレクトリのどちらからも実行できる。管理するランチャーは `init` / `install` の `--intent` で `vouch/config.json` に保存した Intent だけを使い、継承した `VOUCH_INTENT` では対象を変更しない。Intent の切り替えは `init --intent <Intent>` で明示する。旧来の製品フックの直接実行では従来の環境変数の契約を保持する。stdin の root・Intent・harness の主張から使用先を選ばない。

プロジェクト内に本体を置いた Cursor のフックと Claude の statusLine は、プロジェクトルートを作業ディレクトリとして、OS に依存しない `node <本体の相対パス> <操作> project .` を登録する。最後の `.` はその作業ディレクトリの明示指定で、継承した root 環境変数より優先する。共有する登録に POSIX / PowerShell 専用の式を保存しない。個人共通の本体への接続は利用者の環境に依存し、別の利用者・OS ではその環境で `init` を行う。

Cursor には `sessionStart`・`beforeSubmitPrompt`・`preToolUse`・`afterAgentResponse`・`stop` を登録する。入力の `conversation_id` / `generation_id` を共通入力へ写し、ツール名とパス名を変換する。`preToolUse` は許可時に `permission: allow`、拒否時に `permission: deny` と理由の `user_message` を返す。プロジェクト未有効化・重複登録・未知や欠損の入力・内部エラーで guard を実行しない場合も、許可の応答形式を維持する。プロンプトの拒否は `continue: false` と `user_message` へ、再開要約は `additional_context` へ変換する。回答の `text` は脇質問の回答として記録し、本文がない `afterAgentResponse` では回答を確定せず、後続の stop の本文を保存できるようにする。本文がある回答の後は重複追記しない。未知・欠損の入力と内部エラーは既存契約どおり fail-open にし、取得できない測定値や入力識別子を補わない。全ツール・全経路を機械的に強制する境界ではない。

プロジェクト単位の手動コマンドは、作業ディレクトリから祖先をたどり、参照した版のランチャーをNodeのモジュール解決で探す。作業ディレクトリと追加の操作引数を保持し、継承した `VOUCH_PROJECT_ROOT` を使わず、既存ランチャーが最寄りの有効化を検証する。見つかった入口の依存モジュールが欠ける場合は、別の祖先や版へ切り替えず終了2とする。入口がない場合も終了2とし、読み取り専用操作はファイルを変更しない。個人共通の本体への絶対参照は保持する。

ランチャーは信頼済みの入口の配置名（`cursor` / `.cursor`）から Cursor の応答形式を保持する。導入記述子の欠落・不正 JSON・無効なツール名・配置との不一致で処理できない場合も、ネイティブ guard は有効な許可 JSON を返す。手動コマンドは診断を出して終了2とし、stdin や環境変数のツール名で応答形式や作業先を選ばない。

Cursor の `beforeSubmitPrompt` は許可時に `continue: true` を返し、拒否時の `continue: false` と理由を保持する。未有効化・重複・欠損入力・記述子の破損・内部エラーの fail-open でも許可の応答形式を維持する。空の JSON を許可の代わりにしない。

導入・初期化は、設定へ保存する Intent をランチャーと同じ識別子規則で検査する。明示した `--intent` がない場合も保存済みの値を検査し、不正なら `INSTALL-CONFIG` で全ファイルを保持して終了する。doctor も不正な保存値を成功と報告しない。有効な `--intent` を明示した初期化で訂正でき、未選択の空値は許容する。

初期化はプロジェクト内・個人共通のどちらの本体も、保存した配布のハッシュと実際のランチャー・共通ライブラリ・文書の一致を確認してから設定を書き込む。導入記録だけが残り、本体・配布の全部または一部が欠落・改変した場合、成功を報告せず既存ファイルを保持する。doctor と同じ本体検査を共有する。

導入記録の本体パスは、選択した導入先の `.vouch/versions/<digest>/<harness>` と一致することを初期化前に検査する。内容や配布ハッシュが一致した別ディレクトリのコピーでも正規の版パスの代わりには採用せず、`INSTALL-VERSION: runtime path differs` で両スコープのファイルを保持する。登録とプロジェクト設定が別の配置を選ぶ成功報告を防ぐ。

プロジェクト内の初期化は、導入記録が所有するフック登録・Skills・規則・案内文書も変更前に検査する。登録が失われた場合や所有項目が改変された場合は `INSTALL-CONFLICT` で拒否し、残存ファイルを保持する。設定の再有効化によって登録の破損を成功扱いにしない。所有の検査計画は読み取り専用で破棄し、所有ファイルの復元・削除を初期化でコミットしない。

配布された doctor も導入記録の全所有項目を検査する。ファイルは内容一致、案内ブロックは内容の一意な存在、フックは所有した各登録の完全一致と一意性・所有した他の設定値、TOML は所有した設定行と表の曖昧さを導入側と共通の純粋関数で検査する。検査中に復元・削除・追記しない。Codex の hooks 有効化と正の agent depth は、導入前から存在し所有していない設定についても確認する。欠落・改変時は `DOCTOR-ACTIVATION` を失敗とし、他の検査結果とともに終了2で報告する。

新規導入と保存配布の検査は、導入ツール自身が持つ runtime の必須一覧も使う。配布側の inventory が必須のランチャー・共通ライブラリなどを省略した場合、ファイルが存在しない場合、申告したファイルが欠落した場合は `INSTALL-SOURCE` で変更前に拒否する。空または編集した一覧で不完全な配布を成功扱いにしない。

配布 doctor は、導入記録を読み出した場所に応じた scope、digest、runtimeRoot と、プロジェクトが選択した有効化・実行中の正規の版パスを比較する。所有ファイルが一致していても識別情報が不一致なら `DOCTOR-ACTIVATION` と終了2で報告し、既存ファイルを保持する。

両 doctor はプロジェクトの所有一覧の完全性も検査する。保存配布の全 Skills・エージェント、ツール固有のフック登録、`AGENTS.md` の案内ブロックと、Claude の `CLAUDE.md`、Codex の設定、Cursor の規則を、それぞれ正しい種類の一意な所有項目として必要とする。一部の所有記録を削除したり別の項目で置き換えたりして、欠落したファイルを正常と報告しない。検査は読み取り専用とする。

所有項目の内容も導入記録だけを正典としない。検証済み配布と選択した本体・プロジェクト・ツールから、導入時と共通の生成関数でフック、Skills、エージェント、案内ブロック、Cursor規則を再生成して照合する。Codex設定の所有項目も有効化の既知の変更に限る。ファイルと所有記録を同時に変更して、別コマンド・別本体・変更した規則を正常と報告しない。利用者の既存statusLine、無関係なフック・文書・設定と旧TOML所有記録の保持を維持する。

導入・更新・解除・再接続でも、復元計画に渡すすべての所有記録を、その版の検証済み保存配布と生成内容に照合する。個人共通の本体の記録にはプロジェクト専用の案内・規則を要求せず、接続記録にはプロジェクトの完全な有効化を要求する。架空の所有パスや変更した登録を使って Git 設定などを復元・削除しない。新規作成だけが許される Skill・エージェント・規則の所有項目に、任意の元ファイルを復元する記録を認めない。

外部パスの再帰globは `**` の後の条件も照合する。既知の登録に一致する `**/hooks.json` などは拒否し、登録にも本体にも一致しない `**/notes.txt` などを、共通ホーム接頭辞だけを理由に拒否しない。通常のglob・祖先削除・読み取りの扱いは保持する。

導入CLIの doctor も、導入記録の runtimeRoot が選択した正規の版パスと一致することを検査する。scope・digest・runtimeRoot の同じ不一致を両方の doctor が拒否し、診断で既存ファイルを変更しない。

実機検証にはツールの実行ファイル・版・信頼設定と fixture の採取が必要で、この環境では Cursor の実行ファイルがない。新方式の Claude / Codex の実発火も今回の自動テストでは確認していない。正式対応の判定は引き続き上記の検証を条件とする。
