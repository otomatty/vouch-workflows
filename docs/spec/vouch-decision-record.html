01

なぜ Vouch か

v2 は「モデルがステップを飛ばすたびに、機械的な強制（フック・レシート・ガード）を足す」方針で成長した。その結果、エンジンと配布物が肥大化し、AI 駆動開発そのものが重くなった。一方で README 自身が Opus 4.8 を推奨しており、強いモデル前提の設計なのに弱いモデル対策のコストを全員が払っている。

Vouch は「判断はモデル、機械的処理はフック」と役割を分け、v2 の TypeScript エンジン（ルーティング・状態機械）を持たない。フックと監査ログの仕組みは踏襲するが、判断を代行させない。

解決済み：ツール依存とフックの両立 rev 3

rev 2 で衝突していた「ツール依存なし」と「フックを活用」は、利用者側の実行時依存を git ＋ node に限定することで解決した。フックは依存ゼロの plain JavaScript で、パッケージのインストールもビルドも要らない。縮退モードは実装せず、node が無い環境は対象外とする（/vouch status と /vouch doctor が node の有無を検査する）。

03

3つの転換

① エンジンを捨て、Git ＋ フック ＋ 監査ログに置き換えるv2 の TypeScript エンジン（ルーティング・状態機械・レシート）は持たない。状態は成果物の frontmatter から導出し、証跡は git と append-only の監査ログ、機械的な検査・記録・遮断は node のフックが担う。最終ゲートは、人が PR をマージする行為そのもの。
② 品質は「主張 ＋ 証拠 ＋ 参照元」で保証する品質に関するすべての主張に、テスト名・コマンド出力・スクリーンショット・コミットのいずれかの証拠を付ける。すべての成果物に、どの知識（コード・設計・インフラ・背景・規約）を根拠にしたかの参照元を付ける。証拠や参照元のない主張は無効で、フックが機械的に検査する。
③ 人は Review Brief を読み、判断だけをするコードを見なくても判断できる固定構造の文書を Verify の成果物にし、そのまま PR 本文にする。人の関与は Intent 承認と PR 承認の2回に絞り、その間は先送りできない判断依頼だけが届く。判断依頼は選択肢・メリット・デメリット・根拠を添えて、人が調べなくても決められる形にする。
04

原則と禁止リスト

P-1
判断はモデル、機械的処理はフック。手順を強制せず、禁止リストと不変条件だけを持つ。フックは判断しない。検査・記録・遮断だけを行い、判断が要る結果はモデルへ返す。
P-2
成果物が状態、監査ログが証跡と計測。状態機械を持たない。状態は成果物の frontmatter から導出し、出来事とその所要時間は append-only の監査ログに残す。
P-3
主張には証拠を、成果物には参照元を、判断依頼には根拠を付ける。証拠の形式を統一する（test / log / shot / commit）。参照元と根拠は パス:行@コミット か文書 ID か公式文書の URL＋節。rev 3
P-4
常時読み込むものは最小にする。専門知識は必要な時だけ読む。ただし知識レイヤーは常に最新に保つ。
P-5
根本解決の必要最小限。その場しのぎをしない。理想の設計との差分を常に意識し、根本原因を解決するのに必要な最小の変更をする。
P-6
人の時間を最小にする。人の関与は Intent 承認と PR 承認の2回。作業単位は人が1回で判断できる大きさに分割し、H の変更を隔離する。先送りできる質問は Brief に溜める。rev 3
P-7
複雑性の予算を CI で守る。v2 の膨張を繰り返さない。フックにも行数の予算を置く。予算超過は Opus 5.5 での失敗の実証が条件。

禁止リスト（これ以外は禁止しない）

  • テストを通すためにテストを改変・削除する
  • 証拠を捏造する、証拠や参照元のない主張をする
  • 根拠のない選択肢で人に判断を迫る rev 3
  • 人の承認なしに approved にする、承認を代行する
  • 監査ログを手で書く・編集する（モデルも人も）
  • 本番データに触る、main に直接 push する
  • 禁止リストに載っていないことを禁止する

守る不変条件

  • 人の承認なしに approved にならない
  • 承認済みの計画なしに実装しない
  • 契約（型・データ定義）とテストより先に実装をコミットしない
  • 作った者とは別のコンテキストで検証する
  • 受入基準がテスト・検証記録まで追跡できる
  • すべての成果物に参照元があり、参照先が存在する

禁止リストのうち機械的に判定できるもの（テストファイルの削除、main への push、監査ログの手編集、approved への無断変更、根拠欄が空の判断依頼）はフックが遮る。判定に判断が要るもの（その場しのぎかどうか、根拠が妥当か）は reviewer が見る。

05

ライフサイクルと儀式

4ステージ。人間ゲートは Intent と Verify の2回で、Design は計画で必要と判断した時だけ行う。同期の儀式は2つ。モブ・エラボレーションは Intent と Design をまとめて1つの儀式で行い、その中に「確認点」を置いて、ある程度の粒度で人が確認できるようにする。

ステージ成果物何をするか吸収する v2 のステージ
Intent ◆intent.mdexplorer が既存コードを調査（知識レイヤーが古ければ再走査）。人と対話して受入基準（AC-n）を確定。理想形との差分・ユースケースの漏れ・リファクタ候補・根本原因を明記。作業単位の分割案、Unit 分割・リスク階層・AC ごとの検証方法を提案し、確認点を経て1回の承認を得るInitialization ×3、Reverse Engineering、Requirements、User Stories、Practices Discovery、Units Generation、Delivery Planning
Design 条件付きdesign.md高リスク Unit または計画が要求した時のみ。図解を主とし、基準図との差分で示す。契約（型・データ定義・インターフェース）を先に固める。代替案とトレードオフ表を添えるDomain / Contract / Functional / NFR / Infra Design、Mockups
Build ⟳コード、テスト、build-log.mdUnit ごとに builder を worktree で並列実行。契約（型・スキーマ・データ定義が型検査と静的解析を通る）→ テスト（red）→ 実装（green）→ refactor をコミット順で証明。DoD コマンドの出力を記録。フックが順序と検査結果と所要時間を監査ログに残すCode Generation、Build and Test、CI Pipeline
Verify ◆review.md、rules.md への追記別コンテキストの reviewer が敵対的に検証（破壊検査、その場しのぎの検出を含む）。Review Brief を PR 本文にして人が承認。学びを rules.md に追記reviewer 機構、sensors、governance、learnings

儀式（同期的な協働）

儀式いつAI が用意するもの人が確認・決定すること
モブ・エラボレーションIntent と Design をまとめて1回（必要なら分割して継続）1画面 Intent、作業単位の分割案、論点一覧、ユーザー操作のフロー図、用語集、「現状はこう動く」の証拠、理想形との差分、差分図、代替案とトレードオフ表、脅威モデル観点表（H 階層）確認点ごとに確認：AC の確定 → 非ゴール → 理想形と最小実装の線引き → 分割と Unit とリスク階層 → 設計の採択。確認は監査ログに記録

確認点は既定で論点ごとの固定4点（AC 確定 → 非ゴールと最小実装の線引き → 分割・Unit・リスク階層 → 設計採択）。H 階層は Unit ごとの確認を自動で追加する。粒度は rules.md の checkpoints:（topic / unit / section）で変更できる。非同期でも回せる：事前読み → 同期で決定 → 事後反映。決定は decisions.md に人の言葉で記録し、監査ログにも残る。H 階層の Unit ではモブ・コンストラクション（AI の構築を同期で見て方向修正）を任意で行う。

いつでもできること

/vouch ask "<質問>"

脇質問

ワークフロー中に気になったことを、進行中のコンテキストに影響を与えずに聞ける。別コンテキスト（サブエージェント）が intent フォルダと知識レイヤーを読み取り専用で参照して答える。状態は変えない。質問と答えは監査ログに残るので、後で同じことを聞かれない。

/vouch

再開

中断（セッション終了、コンテキスト圧縮、クラッシュ、意図的な停止）の後、引数なしの /vouch でいつでも再開できる。現在地は成果物の frontmatter と監査ログの末尾から導出し、セッション開始フックが再開用の要約を渡す。/vouch status で現在地・確認点・未回答の判断依頼を見る。

06

人のレビューのタイミングと作業単位の分割

rev 3

人が関与するのは、1つの Intent につき同期の接点が2回（Intent 承認、PR 承認）と、その間に届く先送りできない判断依頼だけ。先送りできる質問は Brief に溜めて PR 承認の時にまとめて答える。AI は人の回答を待つ間も他の Unit を止めない。

人のレビューが発生する場面（すべて）

場面いつ人が読むもの人が決めること同期 / 非同期
確認点モブ・エラボレーションの途中1画面の要約（AC 群、分割案、Unit と階層、設計の要点）「この理解で合っているか」同期（非同期でも可）
Intent 承認 ◆モブ・エラボレーションの最後1画面 Intent（＋ 必要時 design.md の差分図）この計画で作ってよいか同期
先送りできない判断依頼Build / Verify の途中。これ以上進めないと止まる時だけ判断依頼カード（§10）選択肢から選ぶ。未回答なら既定案で進み、Brief §7 に明記される非同期。他 Unit は止めない。既定案が作れない時だけ止まる
PR 承認 ◆Verify の後、モブ・レビューReview Brief（L/M）。H はコアロジックの hunk も溜まった判断依頼への回答、マージの可否同期、または PR 上で非同期
Learnモブ・レビューの末尾5分rules.md への追記案採用するか同期

これ以外の場面で人を呼ばない。Build の途中経過、テストの失敗と修正、reviewer との往復、フックの検査結果は監査ログと build-log に残り、人は Brief で結果だけを読む。H 階層でモブ・コンストラクションを行う場合は例外で、人が任意で同席する。

作業単位の分割 — レビューを最小にするために

人のレビューの量を決めるのは「PR の数」ではなく「人が読まなければならない量」。分割の目的は、人がコードを読む箇所を H の変更だけに閉じ込め、それ以外は Brief だけで済ませること。分割案は Intent の最初にモデルが提案し、確認点で人が1回で承認する。

分割の原則

  • 1 Intent ＝ 1 PR ＝ 1 Brief ＝ 1つの振る舞いの変更。Brief が1画面に収まる大きさ（目安：Unit 5 つ以下）
  • リスクで分ける。H の変更は最小の Intent に隔離する。人がコードを読むのはそこだけ。L/M は1つの Intent にまとめる
  • 先に「変更を簡単にする」リファクタを切り出す。振る舞いを変えないリファクタは L の別 Intent にし、テスト全通過で安全を証明する。本体の変更が小さくなる
  • 契約の変更は単独で。公開 API・スキーマ・データ定義の変更は H の Intent として先に固め、後続はそれを参照する
  • 依存順に並べ、後ろを待たせない。後続 Intent は前の PR がマージされる前でも worktree で進める。レビューは順番に、まとめてでも行える
  • 分割案は確認点で1回だけ承認。分割を後から変えたい時はモデルが再提案し、差分だけ確認する

人のレビュー量を減らす他の仕組み

  • 読むべき箇所ガイドで、hunk を core / plumbing / tests / generated / rename に分類し、読まなくてよいものを明示する
  • L 階層は Brief の「主張と証拠」と破壊検査の結果だけで判断できる形にする。マージは人が行う（自動マージはしない）
  • 判断依頼はすべて選択肢と根拠つきで、人が調べる時間をゼロにする（§10）
  • 記録にある答えは再質問しない。脇質問の答えも記録に残る
  • 監査ログで「人がレビューに使った時間」を計測し、Intent の振り返りで分割の粒度を調整する
07

品質モデル — テストだけでは足りない

テストが保証できるのは「仕様どおりに振る舞うか」だけ。次の11の次元を、それぞれ別の証拠で担保する。凡例：テストで担保できる 一部できる できない

08

検証の方針

検証手段には優先順位がある。モデルが自動で検証できるなら、人に確認を求めない。方法の選択はモデルに任せ、禁止するのは「やってはいけないこと」だけ。

V-1 / V-2

自動で検証できるなら自動で

AC ごとに「自動テスト / AI 操作 / 人」のどれで検証するかを Intent で宣言する。テストで担保できない AC は「手動確認」と明示し、判断依頼に必ず載せる。

V-3 / V-4

方法は自由、証拠は必須

モデルは検証方法を自分で選ぶ。AI 操作による検証はスクリーンショット・ログ・実行コマンドを残す。reviewer は builder の証拠を鵜呑みにせず、自分でも再現する。

09

独立検証の仕組みとリスク階層

reviewer は builder の会話を見ない。入力は成果物と diff だけ。Claude Code で作ったものを Codex で検証する（またはその逆）ことを推奨し、モデルの多様性で同じ盲点を共有するリスクを下げる。

リスク階層で厳格さを配分する

階層はモデルが Intent で提案し、人が確認点で承認する。階層は作業単位の分割の基準でもある（§6）。

階層Design破壊検査人のレビュー分割での扱い例
L不要なしBrief をスキムして人がマージ（自動マージなし）まとめてよい文言修正、設定値、テスト追加、振る舞い不変のリファクタ
M任意1箇所Brief ＋ 読むべき箇所ガイドの5分版まとめてよい既存 API の内部変更
H必須3箇所Brief ＋ コアロジックの hunk を人が読む。モブ・コンストラクション任意最小の Intent に隔離認証、決済、データ移行、公開契約の変更

破壊検査（軽量ミューテーションテスト）

reviewer が「ここを壊せばテストが落ちるはずだ」という箇所を選び、実際に壊してテストを実行し、落ちたことを確認して戻す。「テストが本当に何かを検証しているか」を最も安く証明できる。

10

判断依頼の形式

rev 3

人に判断を仰ぐ時は、人が何も調べずに決められる形で出す。選択肢を提示し、各選択肢のメリット・デメリットを根拠（コードの該当箇所、公式文書の該当節）つきで説明し、推奨案と未回答時の既定動作を添える。根拠欄が空の判断依頼はフックが遮る。

判断依頼 Q-3 · 在庫不足時の HTTP ステータス · 階層 M · ブロック: しない（既定案で進めつつ回答を待つ）
状況：在庫不足の注文を拒否する応答コードが未定。既存 API は競合系のエラーに 409 を使っている src/api/errors.ts:12-30@a1b2c3d。フロントは 4xx をすべて同じトーストで表示する web/src/api/client.ts:71@a1b2c3d。
A
409 Conflict 推奨メリット：既存 API の慣例と一致し、クライアント側の変更が不要。リソース状態との衝突を表す意味にも合う。
デメリット：楽観ロック競合の 409 と区別するには error.code が必要。
根拠：RFC 9110 §15.5.10（409 Conflict） · src/api/errors.ts:12@a1b2c3d · rules.md#API エラー規約
B
422 Unprocessable Contentメリット：入力の意味的な不正として扱え、バリデーション系と同じ経路に乗る。
デメリット：既存 API に 422 の前例がなく、フロントのエラー分岐に追加が要る（web/src/api/client.ts:71）。
根拠：RFC 9110 §15.5.21（422） · knowledge/codekb/api-conventions.md#エラー
C
200 ＋ 本文で失敗を返すメリット：なし（挙げるべき利点が見つからない）。
デメリット：HTTP の意味論に反し、監視で失敗が見えない。rules.md#API エラー規約 が禁止している。
根拠：rules.md#API エラー規約@2026-08-30
未回答時の既定：A で実装し、Brief §7 に「Q-3 未回答・既定 A」と明記する。影響範囲：Unit B のみ。他 Unit は継続。

必須の項目

  • 状況：何が未定か、現状はどうなっているか（参照元つき）
  • 選択肢：2〜4 つ。「何もしない」も選択肢として検討し、載せない場合は理由を書く
  • 各選択肢のメリット・デメリット・根拠：根拠はコードの該当箇所（パス:行@コミット）か公式文書（URL＋節）。推測は「推測」と明記
  • 推奨：モデルの推奨と理由
  • 未回答時の既定：必ず既定案を示す。未回答なら既定案で進め、Brief §7 に「Q-n 未回答・既定 X」と明記する。止まるのは既定案が作れない時だけで、その理由を書く
  • ブロックの有無と影響範囲：どの Unit が止まるか、他は継続するか

運用

  • ハーネスの構造化質問（Claude Code の AskUserQuestion、Codex の request_user_input）で選択肢を出し、カード本体は decisions.md に書く
  • 先送りできる判断依頼は Brief §6 に溜め、PR 承認時にまとめて答える。先送りできないもの（これ以上進めない）だけ即時に出し、回答が来なければ既定案で進める
  • 既定案で進めた判断は Brief §7 に一覧で載る。人は PR 承認時に覆せる。覆された場合は builder に戻して修正し、reviewer を再実行する
  • 回答は人の言葉のまま decisions.md に記録し、監査ログに「質問 → 回答」の所要時間が残る
  • 同じ論点は二度と聞かない。過去の回答は参照元として引く
  • Learn で、繰り返し出る論点は rules.md の規約に昇格させる
11

Git・監査ログ・フック

rev 3

Intent ごとにブランチを切り、ゲートはコミット、承認は PR。状態は成果物の frontmatter から導出し、出来事とその計測値は監査ログに残す。契約 → テスト → 実装 の順序はコミット履歴が証明し、フックが検査する。

監査ログ — 後で分析するための計測データ rev 3

監査ログの目的は「何が起きたか」の証跡に加えて、「それにどれだけかかったか」を後から分析できるようにすること。イベントごとに所要時間と、ハーネスから取得できる計測値を構造化して記録する。人が読む記録は decisions.md、機械が読む記録は監査ログ、と役割を分ける。

形式と原則

  • Intent ごとに audit/events.jsonl。1行1イベント、append-only。フックだけが書く
  • イベント種別は正典の台帳で管理し、勝手に増やさない（v2 と同じ）。台帳は約25種の新しい名前（stage.completed、question.answered、hook.check など）で、v2 名は移行時に対応表で変換し、対応のないものは legacy.<NAME> で原文保存する（§18）
  • 各イベントに ts、duration_ms、actor（model / hook / human / reviewer）、intent・stage・unit、親イベント、結果、取得できれば tokens（Claude Code は使用量をフックで取れる）を持つ
  • 人に関わるイベントは「依頼 → 回答」の対で待ち時間が測れる。フックの検査は「開始 → 結果」の対で所要時間が測れる
  • v2 の record を移行する時は、audit シャードも同じ台帳に変換して引き継ぐ（§16）

分析できること（例）

  • Intent の総時間の内訳：AI の作業時間 / 人の待ち時間 / 人がレビューに使った時間
  • ステージ別・Unit 別の所要時間、Build ⟳ Verify の反復回数
  • 判断依頼の回数と回答までの時間、先送りできた割合
  • フック検査（契約・DoD・鮮度・引用）の失敗率と、失敗からの回復時間
  • 破壊検査で検出したテストの穴の数、その場しのぎ検出の数
  • 知識レイヤーが古かった回数、再走査にかかった時間
  • トークン / コスト（取得できるハーネスのみ）、リスク階層別の人のレビュー時間

フックが担う機械的処理

境界は一つ：フックは判断しない。検査・記録・遮断だけを行い、判断が要る結果はモデルへ返す。フックは node で書く依存ゼロの plain JavaScript（ESM）で、ビルドもインストールも要らない。v2 が判断まで代行させて膨らんだ反省から、フックの総量にも行数の予算を置く。

DoD の実行と記録rules.md のコマンドを実行し、出力を build-log と監査ログに残す失敗の原因分析と修正はモデル
知識の鮮度チェックcodekb の世代と git HEAD、設計・インフラ文書の更新日を比べ、古ければ印を付ける再走査の範囲は explorer

知識の鮮度と参照元

既存コード・設計・インフラ・プロジェクト背景・コーディング規約を「知識レイヤー」として常に最新に保ち、AI のすべての成果物に、どの知識を根拠にしたかの参照元を必ず載せる。鮮度と引用の検査はフックが行い、再走査は explorer が行う。判断依頼の根拠も同じ仕組みで検査する。

知識レイヤーに入るもの

  • 既存コード：explorer の調査結果（構造、依存、基準となるアーキテクチャ図、用語集）と世代（コミット）
  • 設計：design 文書、契約（型・スキーマ・インターフェース）、過去の Intent の design.md
  • インフラ：構成・環境・デプロイ方法（Operation は対象外だが、実装が依存する情報は持つ）
  • プロジェクト背景：目的、制約、用語、関係者
  • コーディング規約：rules.md（DoD、禁止リスト、Corrections、依存ルール、確認点の粒度）
  • 公式文書の参照：言語・フレームワーク・RFC など、判断依頼の根拠に使う外部文書の URL と節（本文は持たない）

参照元と根拠のルール

  • すべての成果物に ## 参照元 を置く。空は不可。判断依頼の各選択肢に根拠を置く。空は不可
  • 書式は パス:行@コミット、文書#節@日付、または公式文書の URL＋節。フックが参照先の存在と世代を検査する（外部 URL は到達性のみ）
  • Review Brief の「主張と証拠」に加えて「根拠にした知識」を人が辿れる
  • 知識が古いまま成果物を書いたら、鮮度チェックが監査ログに残し、Brief に警告が載る
  • Learn で rules.md に追記した内容も、次の Intent から参照元になる
13

根本解決と最小実装

既存プロジェクトでは「どう作るのが設計として理想か」を常に問い、ユースケースの漏れとリファクタできる箇所を意識し、その場しのぎではなく根本原因を解決する、必要最小限の実装をする。「最小」とは、根本原因を解決するのに必要な最小の変更であり、将来のための汎化はしない。

Intent / Design に必ず含めるもの

  • 理想形：このコードベースで理想的な作り方と、その根拠（参照元つき）
  • 現状との差分：理想形と現状のずれ。今回埋めるもの／埋めないもの
  • ユースケース網羅表：既存ユースケース × 今回の変更の影響。漏れの候補
  • リファクタ候補：今やる（根本原因に関わる、または変更を簡単にする準備リファクタ）／後回し（理由と記録先）
  • 根本原因分析（バグ修正）：なぜ起きたか、同種の箇所が他にないか
  • 最小実装の線引き：必要なもの／意図的にやらないもの。確認点で人が確認する

reviewer が検出する「その場しのぎ」

  • 特殊ケースの分岐を足して根本原因に触れていない
  • エラーの握りつぶし、リトライで隠す
  • 既存ロジックの複製（共通化すべきものを重複させる）
  • 型の緩和（any 化、キャスト）、静的解析の抑制コメント
  • テストのスキップ・条件の緩和
  • 理想形との差分に書かれていない設計上の妥協

これらは判断が要るのでフックではなく reviewer の観点表で見る。検出した項目は Brief の「主張と証拠」の反例として載せ、人が最終判断する。

  • 必須の図は成果物ごとに固定：基準図＝コンポーネント図、Intent＝ユーザー操作フロー図、Design＝差分コンポーネント図＋シーケンス図、Brief＝主フローのシーケンス図（§18 Q4）

レビュー負荷を下げる工夫

  • 人は主張を読み、証拠と参照元の存在で信頼する。疑わしい行だけ抜き取り検査する
  • 受動的な「全部読む」を、能動的な「質問に答える」に変える。質問の数は制限しないが、答え済みは再質問しない
  • builder と reviewer の2つの独立した記述を並べ、食い違いを見るべき場所として示す
  • デモ手順（demo.sh、curl、操作手順）を添え、人が自分で叩ける
  • Intent ゲートも同じ思想で「1画面」に収める
