Q2

確認点の粒度の既定

モブ・エラボレーション（Intent ＋ Design）の中で、人が「この理解で合っているか」を確認する点をどの粒度で置くか。rules.md で変えられる前提で、既定を決める。
判断依頼 Q2 · 確認点の粒度 ブロック: しない（rules.md の既定値）
状況

v2 は「深さ」で質問量を決めており、Standard で1ステージ 5〜8 問、Comprehensive で 8〜12 問以上を目安にしていた core/vouch-common/protocols/stage-protocol.md:868-870。v2 の Construction では「質問は例外であって日常ではない」と明記している stage-protocol.md:339。Vouch では Intent を1画面に収め、Unit は 5 つ以下を目安に分割する vouch-decision-record.html §6「分割の原則」。確認点は監査ログに checkpoint.confirmed として残り、人の中断回数と待ち時間が計測される。

選択肢
A
論点ごとの固定4点（AC 確定 → 非ゴールと最小実装の線引き → 分割・Unit・リスク階層 → 設計採択）。H 階層の Intent だけ Unit ごとの確認を自動で追加 推奨
メリット人が「何を確認しているか」が毎回同じで学習コストがない。1 Intent あたりの中断が 4 回（Design 不要なら 3 回）で、同期の儀式が 30〜60 分に収まる。H だけ細かくなるのでリスクと手間が比例する デメリット大きな Intent（Unit 5 つ）では「分割・Unit・階層」の確認点が重くなる。ただし Unit 5 つ以下の分割原則があるので上限は決まっている 根拠分割原則 vouch-decision-record.html §6／v2 の質問量の目安 stage-protocol.md:868-870／リスク階層 vouch-decision-record.html §9
B
Unit ごと（AC 確定 1 回 ＋ Unit ごとに Intent 1 回・Design 1 回）
メリットUnit の境界と責務を人が1つずつ確認できる。チーム分業（Unit ごとに担当が違う）に合う デメリットUnit 4 つで 9 回の中断になり、L/M の Intent では過剰。人の待ち時間の割合（目標 20% 未満）を圧迫する 根拠成功指標「人の待ち時間の割合」vouch-decision-record.html §17／v2 の per-unit 反復（unit-major Construction）で Unit ごとの gate が重かった経緯 docs/roadmap.md「2.5.56 Code Generation joins the unit-major Construction walk」
C
成果物の節ごと（intent.md / design.md の見出しごとに1回）
メリット最も細かく、モデルの理解のずれを早く捕まえられる。教育目的（ワークショップ）には向く デメリット10〜20 回の中断になり、v2 の「最大約70回の操作」と同じ問題に戻る。人が判断ではなく確認作業に時間を使う 根拠v2 の操作回数の実測 vouch-decision-record.html §1
推奨と既定
推奨 A。rules.md の checkpoints: で topic（A）/ unit（B）/ section（C）を選べるようにし、既定は topic。H 階層は topic + unit を自動適用。未回答時の既定：A。影響範囲：Intent Skill の進行、rules.md のテンプレート、監査ログの checkpoint.confirmed。
Q3

品質層 × リスク階層

品質モデルの 11 次元（決定記録 §7）を、どのリスク階層で必須にするか。必須にした層は reviewer の観点表で「証拠あり / なし / 該当なし」を必ず埋め、証拠なしは PR 承認前に解消する。
判断依頼 Q3 · 品質層の必須範囲 ブロック: しない（観点表の既定値）
状況

リスク階層はすでに Design の要否・破壊検査の回数・人が読む範囲を決めている vouch-decision-record.html §9。品質層をどの階層で必須にするかを決めないと、reviewer の観点表と Brief の「主張と証拠」の必須行が定まらない。v2 では review_class（advisory / blocking）をコストのダイヤルとして持っていた docs/roadmap.md「reviewer-class cost dial (#718)」。

選択肢
A
階層で段階化する（下の表） 推奨
メリットL の Intent は「正しさ・契約・保守性・判断の根拠」の4層だけで済み、Brief をスキムする運用と釣り合う。H は全11層で、人がコードを読む Intent には reviewer の証拠も揃う デメリット階層の判定を間違えると層が抜ける。ただし階層は人が確認点で承認するので、判定はモデル任せにならない 根拠階層ごとの人のレビュー範囲 vouch-decision-record.html §9／破壊検査の回数 L0 / M1 / H3（決定済み）
B
全 11 層を全階層で必須にする
メリット抜けがなく、観点表が常に同じ形。分析で階層間の比較がしやすい デメリット文言修正の L でも脅威モデル観点表や性能計測を埋めることになり、reviewer の時間と Brief の長さが L でも H 並みになる。「該当なし」が大半を占め、観点表が形骸化する 根拠L の例（文言・設定・テスト追加）vouch-decision-record.html §9
C
正しさと契約の整合だけ必須、他は任意
メリット最も軽い。テストと型検査はフックが自動で証拠を出すので、reviewer の手間がほぼゼロ デメリット「テストだけでは足りない」という Vouch の品質モデルの前提と矛盾する。根本解決かどうか、設計の整合、セキュリティが H でも任意になる 根拠品質モデル §7「テストが保証できるのは仕様どおり動くかだけ」vouch-decision-record.html §7
推奨と既定
推奨 A。未回答時の既定：A。影響範囲：reviewer の観点表テンプレート、Brief §3 の必須行、Intent の AC ごとの検証方法の宣言。

A 案の具体：必須の層（● 必須 / ○ 任意 / — 対象外）

Q4

図の標準セット

「1変更1図」「差分は色で」「詳細度は段階化」の原則のもと、Intent・Design・Brief でそれぞれどの図を必須にするか。
判断依頼 Q4 · 必須の図 ブロック: しない（テンプレートの既定値）
状況

図は Markdown 内の Mermaid で書く方針。GitHub は Markdown の ```mermaid ブロックをそのまま描画する docs.github.com「Creating diagrams」（Writing on GitHub › Working with advanced formatting）。Mermaid が安定して描けるのは flowchart、sequenceDiagram、classDiagram、erDiagram、stateDiagram-v2 で、C4 図は experimental 扱い mermaid.js.org「C4 Diagram (experimental)」。v2 の設計ステージは Domain / Contract / Functional / NFR / Infra の5つに分かれ、それぞれ文書中心だった core/vouch-common/stages/construction/*.md。

選択肢
A
目的別の最小セット（下の表）。Mermaid の安定5種だけを使う 推奨
メリット各成果物に「必ずある図」が決まるので、読む人が図の場所と意味を覚えられる。GitHub でそのまま描画され、差分は色（classDef）で示せる。C4 の experimental な記法に依存しない デメリットC4 の container 図のような「システム全体の俯瞰」は flowchart で代用するので、C4 に慣れたチームには物足りない。図の種類が固定なので、UI 中心の変更ではスクリーンショットで補う必要がある 根拠GitHub の Mermaid 対応 docs.github.com「Creating diagrams」／Mermaid の図の種類 mermaid.js.org「Diagram Syntax」／図解の原則 vouch-decision-record.html §14
B
C4 フルセット（Context / Container / Component / Code）を Design で毎回作る
メリット体系が確立していて、アーキテクチャ全体を段階的に俯瞰できる。基準図（知識レイヤー）を C4 で持てば差分図も同じ体系で描ける デメリットMermaid の C4 は experimental で描画が不安定。1 Intent の変更に対して4階層は過剰で、Design が条件付き（必要時のみ）という Vouch の方針と合わない。人が読む量が増える 根拠mermaid.js.org「C4 Diagram (experimental)」／Design は条件付き vouch-decision-record.html §5

種類は決めず「1変更1図」だけを規定し、図の選択はモデルに任せる
メリット最も柔軟で、P-1（判断はモデル）に沿う。変更の性質に最適な図を毎回選べる デメリット成果物ごとに図の種類が変わり、読む側が毎回「この図は何を示すか」を読み解く必要がある。レビュー負荷軽減の目的（人が構造を覚えて速く読む）に反する 根拠Review Brief の固定構造の狙い vouch-decision-record.html §14
推奨と既定
推奨 A。必須の図に加えて、モデルが必要と判断した図を足すのは自由（C の柔軟さは「追加」として残す）。未回答時の既定：A。影響範囲：intent.md / design.md / review.md のテンプレート、知識レイヤーの基準図の形式。

Q5

AI 操作による検証の環境

「自動テスト → AI がアプリを操作 → 人」の2段目を、どこで実行するか。ブラウザ操作・CLI 実行・API 呼び出しと、そのスクリーンショットやログを証拠として残す場所。
判断依頼 Q5 · AI 操作検証の環境 ブロック: しない（Build / Verify Skill の既定）
状況

Claude Code の実行環境では Chromium と Playwright が同梱され、追加インストールなしにブラウザ操作ができる（本セッションの環境でも PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers が設定済み）。Codex はサンドボックス（workspace-write）で .git が読み取り専用になるなど制約があり、headless 実行には writable_roots の設定が要る harness/codex/skills/vouch/SKILL.md:199。v2 の Build and Test はテスト実行が中心で、AI がアプリを操作する検証は定義していなかった core/vouch-common/stages/construction/build-and-test.md。証拠の書式は shot: と log: で統一済み vouch-decision-record.html §7。

選択肢
A
ローカル既定。サービス依存があればコンテナを builder が起動。CI は PR で同じ手順を再実行する 推奨
メリット開発中の往復が最速で、builder が壊れたらその場で直せる。DB などが要る時だけコンテナを使うので普段は軽い。CI で同じ demo.sh を回すので、Brief の証拠が第三者にも再現できる デメリット3つの環境の差（ポート、環境変数、データ）を knowledge/infra/ で管理する必要がある。Codex ではサンドボックス設定を配布物に含める必要がある 根拠Playwright 同梱の実行環境（本セッションの環境情報）／Codex サンドボックスの制約 harness/codex/skills/vouch/SKILL.md:199／知識レイヤーのインフラ項目 vouch-decision-record.html §12
B
常にコンテナ（devcontainer / compose）で検証する
メリット環境差がなく、証拠の再現性が最も高い。本番に近い構成で探索的検証ができる デメリット文言修正の L でもコンテナを起動することになり、往復が遅い。プロジェクトに compose 定義がないと使えず、導入の障壁になる 根拠L 階層の例と分割原則 vouch-decision-record.html §6, §9

CI だけで検証し、AI はローカルで操作しない

Q6

Brief と判断依頼の言語

人が読む成果物（Intent、Brief、判断依頼、decisions.md）の言語を固定するか、設定にするか。
判断依頼 Q6 · 人が読む成果物の言語 ブロック: しない（rules.md の既定値）
状況

v2 には言語設定がなく、成果物は英語で書かれる前提だった core/vouch-common/protocols/stage-protocol.md（英語のテンプレート）。このチームの決定記録と判断依頼は日本語で運用している。識別子（AC-1、Q-3、D-4、イベント種別、ファイルパス）は言語に関係なく英数字で、監査ログの分析にも使う。

選択肢
A
rules.md の language: で選択。既定は日本語。識別子・イベント種別・コミットメッセージの型は英語固定 推奨
メリットチームの言語で Brief と判断依頼が読める。英語圏のチームや OSS プロジェクトでも同じ配布物が使える。識別子が英語固定なので、監査ログの分析と grep は言語に依存しない デメリットテンプレートの見出し（「主張と証拠」など）を言語ごとに持つ必要がある。日本語と英語の2つを最初に用意し、他は後回しになる 根拠証拠と参照元の書式が英数字 vouch-decision-record.html §7／Brief の固定構造 vouch-decision-record.html §14
B
日本語固定
メリットテンプレートが1つで済み、最も単純。このチームの用途には十分 デメリット英語話者のメンバーや OSS 公開時に使えない。upstream（awslabs）へ還元する道が閉じる 根拠上流リポジトリは英語 README.md
C
英語固定（コードや規約と同じ言語に揃える）
メリットコード・コミット・PR と言語が揃い、モデルの出力も安定しやすい。upstream 互換 デメリットこのチームの人が Brief を読む速度が落ち、「コードを読まなくても判断できる」というレビュー負荷軽減の目的に反する 根拠転換③「人は Review Brief を読み、判断だけをする」vouch-decision-record.html §3
